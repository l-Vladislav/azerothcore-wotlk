# mod-remote-control - админ-панель управления сервером из игры

Статус: Phase 0 + Phase 1a + Phase 2a (2026-08-25). PTR-инструмент, на live не
выкатывается без отдельного решения.

## 1. Назначение и границы

Внутриигровая панель администратора: время суток, погода (через
mod-advanced-weather), выдача предметов, каст
спеллов, спавн НПЦ, телепорты. Клиент 3.3.5a.

Ключевой факт, определяющий архитектуру: **почти всё это уже реализовано в ядре как
GM-команды**. Новый серверный код нужен только там, где команды отсутствуют или
неудобны для UI. Всё остальное - оболочка.

Что уже есть в ядре и переиспользуется как есть:

| Задача | Команда | Уровень | Файл |
|---|---|---|---|
| Погода | `.wchange <тип> <сила>` | ADMIN | `cs_misc.cpp:1910` |
| Предмет в сумку | `.additem <id> <кол-во>` | GM | `cs_misc.cpp:170` |
| Каст | `.cast`, `.cast self/target/dist/back` | - | `cs_cast.cpp` |
| Аура | `.aura` / `.unaura` | - | `cs_misc.cpp:148` |
| Поиск | `.lookup item / spell / creature / gobject / quest / tele` | MODERATOR | `cs_lookup.cpp` |
| Спавн | `.npc add`, `.gobject add` | GM | `cs_npc.cpp`, `cs_gobject.cpp` |
| Перемещение | `.tele`, `.go xyz`, `.appear`, `.summon` | - | `cs_go.cpp`, `cs_tele.cpp` |
| Модификация | `.modify ...`, `.cheat god/fly` | - | `cs_modify.cpp`, `cs_cheat.cpp` |

Чего в ядре нет и что делает модуль:

* **Время суток** - команды не существует. Реализуется повторной отправкой
  `SMSG_LOGIN_SETTIMESPEED` (см. §6).
* **Закрепление погоды** - `.wchange` временный, `Weather::Update` перекатывает
  состояние по таймеру `CONFIG_INTERVAL_CHANGEWEATHER` (см. §5).
* **Машиночитаемые ответы** - `.lookup` печатает текст для человека; аддону нужен
  разбираемый протокол.

### Граница с админ-панелью (`tools/admin-panel`)

* Панель (FastAPI) - массовые и структурные правки: правила env-effects, канбан,
  редакторы контента.
* Аддон - живые операции в мире здесь и сейчас.

Редакторы правил в Lua не тащим.

## 2. Транспорт

Та же схема, что отлажена в `ItemTalentUI` (`modules/mod-item-talents`):

```
клиент:  SendChatMessage(".rc weather set 2 0.75", "SAY")
сервер:  handler->PSendSysMessage("RC:OK") / "RC:B:<запись>\t<запись>\t..."
клиент:  ChatFrame_AddMessageEventFilter("CHAT_MSG_SYSTEM", ...) - ловит и прячет
```

Почему не настоящие addon-сообщения: `CMSG_MESSAGECHAT` с типом ADDON сервер не
разбирает, потребовался бы хук и свой роутер. Chat-команды дают бесплатно парсинг
аргументов, проверку прав и работу из консоли.

Правила, перенесённые из перф-разбора item-talents (2026-07-09):

* **Батчинг** `RC:B:<a>\t<b>\t...`, лимит чанка 250 байт (лимит чат-строки 3.3.5).
* **Пагинация** результатов поиска - 20 на страницу. В базе 217k предметов от
  mod-worn-drops, "выдать всё" недопустимо.
* **Дебаунс** ввода в строке поиска 300 мс.
* Кэш избранного и истории - в SavedVariables, не запрашивать сервер на открытие окна.

## 3. Безопасность

1. Клиент не доверенный: любой игрок может набрать `.rc ...` руками. Вся защита
   только серверная, "пароля в аддоне" не существует.
2. Каждая команда регистрируется с `SEC_ADMINISTRATOR` в таблице **и**
   дополнительно проверяет права в теле (`RemoteControlMgr::IsAllowed`). Таблица
   защищает от вызова, проверка в теле - от ошибки в таблице при рефакторинге.
3. `RemoteControl.Enable = 0` по умолчанию. Опциональный whitelist аккаунтов
   `RemoteControl.AllowedAccounts`.
4. Аудит: Phase 0 - строка в лог воркера (логгер `module.remote_control`). Таблица
   в БД - позже, если понадобится история с выборкой; отдельная таблица тянет за
   собой риск "SELECT по отсутствующей таблице роняет worldserver" (известная
   грабля проекта).
5. Broadcast-действия (время/погода на всех) - Phase 3, отдельный флаг конфига и
   подтверждение в UI.

## 4. Фазы

* **Phase 0** (сделано) - каркас модуля, `.rc`, конфиг, аудит в лог, вкладка "Мир":

* **Phase 1a** (сделано) - вкладка "Спеллы": каталог, поиск, каст/аура/выучить.

  шаговое перемещение / поворот / наклон / масштаб, закрепление в БД. См. §11.

* **Phase 1b** - вкладка "Предметы": поиск по `item_template` с русскими

* **Phase 2b** - НПЦ, телепорты, список игроков онлайн.
* **Phase 3** - пресеты и "сцены" (погода + время + событие одной кнопкой),

  gear ascension, nemesis, env-effects), broadcast-режим.

## 5. Погода

**Погоды в mod-remote-control больше нет (2026-08-20).** Ею целиком
распоряжается `mod-advanced-weather`: у него свой режиссёр, все 13 состояний
`WeatherState` и свой протокол `.aw`. Серверная часть погоды из этого модуля
удалена — два модуля, возвращающих зоне «свою» погоду через один и тот же хук
`ALEScript::OnWeatherChange`, воевали бы друг с другом. Аддон остался общим:
вкладка «Мир» шлёт `.rc` для времени и `.aw` для погоды.

Что осталось верным и переехало в новый модуль:

* **Закрепление.** `Weather::Update` каждые `CONFIG_INTERVAL_CHANGEWEATHER`
  зовёт `ReGenerate()`, и погода уезжает. Решение режиссёра возвращается из
  глобального хука `ALEScript::OnWeatherChange` — он вызывается для всех зон.
  `WeatherScript::OnChange`, наоборот, database-bound: срабатывает только для
  зон с прописанным `game_weather.ScriptName`, поэтому не годится.
* `Weather::UpdateWeather` **мутирует** `m_grade` (клампит в `0.0001..0.9999`).
  Значение вне диапазона никогда не совпадёт с текущим и даст бесконечную
  рекурсию через `OnWeatherChange` — отсюда клампы и re-entrancy guard
  (`_applying` в `AdvancedWeatherMgr`).
* `Weather::SetWeather` выходит рано при совпадении type и grade — повторное
  применение бесплатно.
* **Связь с mod-environmental-effects.** Он слушает смену погоды и делает
  `ReconcileZone`. Конфликта нет: смена погоды потянет за собой env-эффекты —
  это ожидаемое поведение. Его триггеры 4-7 (туман, гроза, чёрный дождь, чёрный
  снег) без нового модуля не срабатывают вовсе: ядро такую погоду не
  генерирует.

Новое, чего в ядре не было: `Map::GetZoneOverrideWeather` /
`GetZoneOverrideWeatherGrade` — геттеры наложенной на зону погоды. Наложение
(`Map::SetZoneWeather`) — единственный способ выразить туман и чёрный снег и
единственное, что доедет до игрока, вошедшего в зону позже.

**Связи зон (2026-08-21).** Погода источника переезжает соседям по таблице
`mod_advanced_weather_zone_link` с ослаблением по ступеням: 100% — та же самая,
49% — гроза приходит обычным дождём. Один шаг, ручную и закреплённую погоду не
перебивает. Для аддона это протокол **3**: строка `AW:ZONE` выросла на два поля
(зона-источник и сила связи), а `AW_SOURCES` получил значение 3 «по связи».
Правится всё это в админ-панели; подробности — README модуля.

Правило панели **выбор отделён от применения** осталось: кнопки семейств,
кнопки особых состояний и ползунок силы только набирают выбор (подсветка рамкой
+ строка "выбор: ..."), команда уходит единственной кнопкой "Применить". Пока
её не нажали, панель не шлёт ни одной команды смены погоды и зоной
распоряжается режиссёр. Рядом кнопка "Вернуть режиссёру" — `.aw release`.
Быстрые кнопки дока — исключение по смыслу: там сам клик и есть применение.
Градация внутри семейства берётся из ползунка (до 40% слабая, до 70% средняя,
дальше сильная — те же границы, что в `Weather::GetWeatherState`).

Погода живёт только там, где есть игроки: без них некому слать пакет и не с
какой карты его брать. Команда в пустую зону отвечает `AW:ERR:NOPLAYERS`.

## 6. Время суток

Клиент получает время один раз пакетом `SMSG_LOGIN_SETTIMESPEED`
(`Player.cpp:11541`: packed time + скорость `0.01666667`) и дальше крутит часы сам.
Смена времени = повторная отправка этого пакета конкретному игроку.

Ограничения, которые надо помнить:

* Эффект **чисто клиентский и персональный**. Серверные `game_event` продолжают
  идти по реальному времени.
* Пакет входит в `SendInitialPacketsBeforeAddToMap`, то есть **любая смена карты
  сбрасывает подделку**. Модуль переотправляет её в `OnPlayerMapChanged` и
  `OnPlayerLogin`.
* Состояние живёт в памяти и очищается на логауте (PTR-инструмент, БД не нужна).
* `AppendPackedTime` кодирует год/месяц/день/день недели/час/минуту через
  **локальное** время процесса - сдвиг считается в минутах поверх серверного
  времени, дата сохраняется.
* Множитель скорости суток (`.rc time speed`) масштабирует поле game speed.
  При множителе больше 1 сдвиг постепенно уезжает - это нормально, режим нужен для
  наблюдения за циклом дня и ночи.

## 7. Протокол

Все ответы - системные сообщения с префиксом `RC:`, аддон их прячет.

| Команда | Ответ |
|---|---|
| `.rc hello` | `RC:HELLO:<proto>:<security>` |
| `.rc time set <час> [минута]` | `RC:TIME:<час>:<минута>:<сдвиг в мин>:<скорость x100>` |
| `.rc time speed <множитель>` | то же |
| `.rc time reset` | то же |
| `.rc time status` | то же |
| `.rc go ...` | см. §11 |
| любая ошибка | `RC:ERR:<код>` |

Коды ошибок: `DISABLED`, `DENIED`, `NOPLAYER`, `BADARG`, а также объектные
`NOTFOUND`, `NOSEL`, `LIMIT`, `SPAWNFAIL`, `ALREADYSAVED`, `BADMAP`, `NOMODEL`.

Версия протокола - **3** (1: без объектов, 2: объекты, 3: прицел и превью).

Погодная половина вкладки говорит протоколом `mod-advanced-weather` (префикс
`AW:`, тот же чат-фильтр); он описан в README этого модуля:

| Команда | Ответ |
|---|---|
| `.aw hello` | `AW:HELLO:<proto>:<включён 0/1>` |
| `.aw status [зона]` | `AW:ZONE:<зона>:<состояние>:<сила %>:<источник>:<секунд>:<есть климат>` |
| `.aw set <зона> <состояние> <сила 0..100> [минут]` | то же |
| `.aw pin <зона>` / `.aw release <зона>` | то же |
| любая ошибка | `AW:ERR:<код>` |

`зона = 0` в игре означает «зона говорящего». Коды: `DISABLED`, `BADARG`,
`NOZONE`, `NOPLAYERS`, `NOTTRACKED`, `WEATHEROFF`.

## 8. Вкладка "Спеллы" (Phase 1a)

Единственная вкладка, которой **не нужен серверный код**: и данные, и действия
уже есть.

* **Данные** - клиентский `Spell.dbc`. `GetSpellInfo(id)` возвращает имя, ранг и
  иконку без запроса к серверу. Кастомные спеллы проекта (фамильяры 102000+,
  таланты предметов 108900+) в клиентском MPQ есть, так что они находятся
  наравне с обычными.
* **Действия** - штатные GM-команды ядра, все `SEC_GAMEMASTER`:
  `.cast <id>` (в цель), `.cast self <id>`, `.aura <id>`, `.unaura <id>`,
  `.unaura all`, `.learn <id>`, `.unlearn <id>`.
  `.cast`/`.aura`/`.unaura` работают по выделенной цели, а без выделения - по
  самому GM: `ChatHandler::getSelectedUnit` падает обратно на кастующего.

Следствие: вкладка работает даже при `RemoteControl.Enable = 0`, и её изменения
не требуют пересборки worldserver.

Реализация каталога:

* Строится **лениво**, на первом открытии вкладки, кусками по 3000 id за кадр
  (`MAX_SPELL_ID = 130000`, около 44 кадров). Разом это дало бы заметный фриз.
* Хранится как два плоских массива (id и имя), а не массив таблиц: имена в Lua
  интернируются, поэтому ранги одного спелла делят одну строку.
* Запрос из одних цифр трактуется как id и каталог вообще не трогает.
* Ввод дебаунсится на 300 мс, результатов не больше 400, на странице 12.
* `string.lower` кириллицу в 3.3.5 не трогает, поэтому имя сверяется дважды -
  как есть и в нижнем регистре. Для латиницы выходит регистронезависимо, для
  русских имён - точное вхождение.

## 9. Док быстрых кнопок

Полоса иконок поверх интерфейса (`RemoteControlUIDock`), чтобы рутинные действия
не требовали ни `/rc`, ни открытия большого окна: панель, 4 семейства погоды,
переключатель закрепления, 4 особых состояния, возврат зоны режиссёру,
4 пресета времени, сброс времени.

* Перетаскивается мышью, позиция и видимость - в SavedVariables.
* ПКМ по первой кнопке сворачивает док до неё одной.
* `/rc dock` скрыть/показать, `/rc lock` закрепить, `/rc pos` сбросить позиции.
* Кнопка закрепления подсвечивается по фактическому состоянию с сервера
  (`AW:ZONE` -> `Refresh` -> `UpdateDock`), а не по локальному предположению.
* Быстрые кнопки погоды шлют силу 80%: всё ниже 27% сервер покажет как "ясно".
* Док - единственное место, где клик по погоде сразу её применяет: он для этого и
  сделан. В большой панели применение отделено от выбора (§5).

Две ловушки клиента, из-за которых код выглядит сложнее, чем задача:

* **Рукопожатие нельзя слать в `PLAYER_LOGIN`** - чат в этот момент ещё не готов
  и `SendChatMessage` пропадает. Шлём через 3 с после `PLAYER_ENTERING_WORLD`, и
  только на первом входе (телепорты шлют это событие повторно).
* Это рукопожатие уходит **само**, без участия игрока, поэтому ровно одно
  сообщение об ошибке после него гасится (`quietErrOnce`): иначе выключенный
  модуль ругался бы в чат на каждом логине. Состояние всё равно видно в строке
  внизу панели.

## 11. Вкладка "Объекты" (Phase 2a)

Поставить в мир любую модель из `gameobject_template` (сундук, бочка, ящик,
костёр) и подвигать её из аддона. Заготовка под будущие мировые предметы,
которые можно разместить и потом залутать.

### Почему не хватило команд ядра

`.gobject add / move / turn` в ядре есть, но:

1. Они **пишут в таблицу `gameobject` на каждое действие** - два похода в БД на
   один сдвиг (`SaveToDB` до пересоздания и `AddGameobjectToGrid` после,
   `cs_gobject.cpp:423`). В панели объект двигают десятками нажатий подряд.
2. Они адресуются `spawnId` из БД, а у временного объекта его нет.
3. `.lookup object` печатает текст для человека. Аддону нужен разбираемый ответ
   с пагинацией: в `gameobject_template` десятки тысяч строк.

### Ограничение, из которого растёт весь UX

Клиент 3.3.5a **кэширует удалённые объекты по GUID и воскрешает их на старом
месте**, игнорируя новый блок создания - комментарий прямо в ядре
(`cs_gobject.cpp:461`). Поэтому:

* Любая правка позиции, поворота или масштаба = despawn + spawn с **новым**
  GUID. Плавного перетаскивания мышью на 3.3.5 не выйдет в принципе.
* Движение шаговое: кнопки направлений + переключатель размера шага
  (0.1 / 0.5 / 1 / 5 м). Каждое нажатие - одна команда.
* Зато у временного объекта пересоздание не стоит ничего, кроме пакета клиенту:
  ни одного запроса в БД, в отличие от `.gobject move`.

Направления задаются **в системе игрока** (`.rc go move <вперёд> <влево>
<вверх>`), а не в осях карты: кнопка "Вперёд" означает то, что видно на экране.
Пересчёт делает сервер - клиент не знает свою ориентацию достаточно точно.

### Временный спавн, закрепление отдельно

Объект создаётся напрямую (`Create` + `AddToMap`), как в
`Map::SummonGameObject`, но **без владельца**: `WorldObject::SummonGameObject`
вешает GO на игрока через `Unit::AddGameObject`, и такой объект снимается
вместе с логаутом хозяина - для расставляемого пропа это не то.
`SetSpawnedByDefault(false)` и `respawnTime = 0`: объект не тикает таймером
респавна и не воскресает сам.

Расплата за временность: объект не переживает выгрузку грида и рестарт воркера.
Поэтому запись `RemoteControl::PlacedObject` хранит позицию **сама** и умеет
поднять объект заново (`RemoteControlMgr::Respawn`) - она, а не мир, источник
истины.

Кнопка **"Закрепить"** (`.rc go save`) - единственное место вкладки, которое
пишет в БД. Порядок в точности как в `.gobject add`: `SaveToDB`, снести
временный экземпляр, поднять чистый через `LoadGameObjectFromDB` и
`AddGameobjectToGrid`. После этого объект перестаёт быть временным и модулю
больше не принадлежит: двигать его дальше нужно штатным `.gobject move`.
Попытка подвинуть закреплённый объект отвечает `RC:ERR:ALREADYSAVED` - иначе
позиция в памяти и строка в `gameobject` разъехались бы.

Незакреплённые объекты снимаются на логауте хозяина: они и так не переживут
рестарт, а брошенный посреди мира сундук без владельца потом никто не найдёт.

### Каталог

Поиск идёт по `sObjectMgr->GetGameObjectTemplates()` - шаблоны уже в памяти, в
БД никто не ходит (так же устроен `.lookup object`, `cs_lookup.cpp:650`).
Локализованное имя из `locales_gameobject` проверяется вместе с английским: у
русского клиента "бочка" находится по локали, "barrel" - по шаблону.

* Страница 12 записей, потолок совпадений 600: запрос из одной буквы иначе
  высыпал бы тысячи страниц.
* Совпадения сортируются по entry - порядок обхода `unordered_map` не
  определён, а страницы должны быть устойчивы между запросами.
* Фильтр по `gameobject_template.type` - кнопка-переключатель, а не
  `UIDropDownMenu`: тот на 3.3.5 капризен, а вариантов немного.
* Избранное живёт в SavedVariables аддона, сервер о нём не знает. Стартовый
  набор - дюжина ходовых пропов; ПКМ по строке каталога добавляет и убирает.

### Протокол

| Команда | Ответ |
|---|---|
| `.rc go search <стр> <тип> <запрос>` | `RC:GOF:<запись>\t...` пачками, затем `RC:GOP:<стр>:<всего стр>:<найдено>` |
| `.rc go spawn <entry> [дистанция]` | `RC:GOS:<запись объекта>` |
| `.rc go list` | `RC:GOL:<запись>\t...` пачками, затем `RC:GOE:<сколько>:<выбранный>` |
| `.rc go sel <handle>` / `.rc go info` | `RC:GOS:<запись>` |
| `.rc go move <вперёд> <влево> <вверх>` | `RC:GOS:<запись>` |
| `.rc go at <x> <y> <z>` | `RC:GOS:<запись>` |
| `.rc go tome [дистанция]` / `ground` / `goto` | `RC:GOS:<запись>` |
| `.rc go turn <градусы>` / `face` | `RC:GOS:<запись>` |
| `.rc go tilt <гр Y> <гр X>` / `scale <k>` | `RC:GOS:<запись>` |
| `.rc go save` | `RC:GOS:<запись>` |
| `.rc go aim [дистанция]` / `drop` | `RC:GOAIM:<handle>:<0/1>:<дистанция>` |
| `.rc go model <entry>` | `RC:GOM:<entry>:<0/1 можно показать>:<радиус>:<высота>:<путь>` |
| `.rc go del [handle]` | `RC:GODEL:<handle>` |
| `.rc go clear` | `RC:GOCLR:<сколько сняли>` |

Запись каталога (`RC:GOF`): `entry|имя|тип|displayId`.

Запись объекта (`RC:GOS` / `RC:GOL`), 14 полей через `|`:
`handle|entry|имя|x|y|z|поворот°|наклонY°|наклонX°|масштаб|закреплён|тип|displayId|дистанция`.

Углы наружу уезжают в **градусах**: аддону так удобнее, точности хватает.
Записи в батче разделены табуляцией, чанк - 200 байт (правило §2). Разделители
`|` и таб выбиваются из имён на сервере (`RemoteControl::Sanitize`).

`handle` - короткий номер, свой у каждого админа; ObjectGuid наружу не уезжает,
потому что он меняется при каждом сдвиге.

### Режим прицела - и почему не мышью

Первое, о чём спрашивают: нельзя ли показывать полупрозрачную модель под
курсором и ставить её кликом, как в строительных играх. **Нельзя, и упирается
это в три независимых стены:**

1. **Мирового рейкаста в API 3.3.5 нет.** `GetCursorPosition()` отдаёт только
   экранные координаты; функции "точка мира под курсором" Blizzard не давала ни
   в одной версии. Все, кому она нужна, читают память клиента - то есть делают
   это вне аддона.
2. **Аддон не рисует в мире.** `Model`-фрейм - это UI-слой: поверх всего, со
   своей камерой, без перекрытий геометрией. Призрака на земле из него не
   выйдет.
3. **Прозрачного геймобъекта не бывает.** В блоке `GAMEOBJECT_*`
   (`UpdateFields.h:398-405`) есть displayid, флаги, вращение, фракция,
   уровень. Масштаб живёт в `OBJECT_FIELD_SCALE_X`, **альфы нет ни там, ни
   там**. Полупрозрачным на 3.3.5 умеет быть только юнит.

Что сделано взамен: **прицел по взгляду** (`.rc go aim`). Камера и так
крутится мышью, поэтому объект ездит не за курсором, а за направлением взгляда,
на `RemoteControl.AimDistance` метров вперёд, с посадкой на землю и разворотом
лицом к хозяину. Кнопка "Зафиксировать" (`.rc go drop`) оставляет его на месте.

**По умолчанию прицел выключен.** Обычный сценарий - объект появляется там,
куда вы смотрите, и дальше двигается кнопками; прицел включают осознанно, под
конкретную расстановку. Галочка "сразу в прицел" запоминается в SavedVariables.
Сам спавн при этом идёт в ту же точку, что считает прицел (`AimPoint`): перед
игроком, на землю, лицом к нему - иначе на склоне объект повисал бы в воздухе
на высоте ног.

Ключевая деталь реализации - **объект переезжает не каждый тик, а когда игрок
замер**. Каждая перестановка это despawn+spawn с новым GUID, то есть видимое
моргание; непрерывный пересчёт дал бы строб. `RemoteControlMgr::UpdateAim`
(зовётся из `WorldScript::OnUpdate`) отслеживает позицию и ориентацию хозяина,
и переставляет объект, только когда тот не шевелился `AimSettleMs` (200 мс по
умолчанию). Получается одно моргание на каждую остановку.

Пороги "не шевелился" - 0.05 м и 0.03 радиана: без них дрожание позиции
стоящего персонажа не давало бы объекту успокоиться никогда.

Правила выключения прицела (все - в одну сторону, тихо):

* хозяин вышел, сменил карту, объект удалили или закрепили - `UpdateAim` сам
  вычищает запись;
* **любое ручное перемещение или поворот** (`move`, `at`, `tome`, `ground`,
  `turn`, `face`) - иначе прицел вернул бы объект под взгляд на ближайшей
  остановке, и кнопка выглядела бы сломанной. Сервер шлёт `RC:GOAIM` следом,
  чтобы панель погасила подсветку;
* наклон и масштаб прицелу ортогональны и его **не** трогают.

Пока прицел включён, кнопки "Вперёд"/"Назад" в панели меняют не позицию, а саму
дистанцию прицела - двигать объект вручную в этом режиме бессмысленно.

### 3D-превью модели

Иконок у геймобъектов нет, а в каталоге три сотни разных "бочек" - без
картинки выбирать невозможно. Путь к модели аддону самому не достать
(`GameObjectDisplayInfo.dbc` ему недоступна), но **сервер её держит
загруженной**: `GameObjectDisplayInfoEntry::filename` и габариты
`minX…maxZ` (`DBCStructure.h:1038`, формат `"nsxxxxxxxxxxffffffx"` в
`DBCfmt.h:56`). Команда `.rc go model <entry>` отдаёт путь и габариты, аддон
скармливает путь `Model:SetModel`.

Что лежит в этой DBC на самом деле (посчитано по файлу, 3790 строк):
**3575 `.mdx`, 167 `.wmo`, 31 `.mdl`, 17 пустых**. Отсюда две поправки на
сервере:

* `.wmo` - это здание. `Model`-фрейм такие не рисует, поэтому отвечаем
  `RC:GOM:<entry>:0:0:0:<путь>` и панель честно пишет "нет превью".
* `.mdl` - историческое написание; файл в MPQ лежит как `.mdx`. Переписываем.

**Три вещи, без которых Model-фрейм показывает пустоту** (первая версия
превью не работала именно поэтому):

1. **`SetLight`.** Без источника света модель рисуется чёрной на тёмном фоне -
   выглядит ровно как "ничего не загрузилось". Вектор и интенсивности взяты
   штатные: `SetLight(true, false, 0, -0.707, -0.707, 0.7, 1,1,1, 0.8, 1,1,0.8)`.
2. **`SetPosition` после КАЖДОГО `SetModel`.** Позиция отсчитывается от левого
   нижнего угла фрейма, поэтому модель, которой её не задали, стоит в углу и в
   кадр почти не попадает. `SetModel` сбрасывает и позицию, и свет, так что
   задавать их заранее бесполезно - только после.
3. **Рамка отдельным фреймом позади модели.** `SetBackdrop`, повешенный на сам
   `Model`, накрывает трёхмерную сцену.

Ещё две грабли, найденные уже в игре:

* **`SetLight` принимает числа, а не булевы.** Булевы завезли в 7.0.3; на 3.3.5
  `SetLight(true, false, ...)` отвечает `Usage: ...` и роняет скрипт целиком, а
  с ним и всю загрузку модели - до `SetFacing`/`SetPosition` дело не доходит.
  Рабочая форма - девять числовых аргументов. Поэтому же каждая ручка виджета
  зовётся через `pcall`: одна неудачная не должна уносить остальные.
* **Оси `SetPosition` не те, что кажутся.** Это стоило трёх итераций вслепую,
  так что здесь дословно из документации виджета:

  | аргумент | что делает |
  |---|---|
  | `x` | горизонталь, плюс вправо |
  | `y` | вертикаль, плюс вверх |
  | `z` | глубина, плюс ближе к камере |

  Начало координат - **левый нижний угол рамки**, не её центр и не камера.

**Размер рамки в модельных координатах** считается через диагональ экрана:

```lua
local scale = UIParent:GetEffectiveScale()
local hyp = ((GetScreenWidth() * scale) ^ 2 + (GetScreenHeight() * scale) ^ 2) ^ 0.5
local w = (frame:GetRight() - frame:GetLeft()) / hyp
local h = (frame:GetTop() - frame:GetBottom()) / hyp
```

Числа выходят крошечные: для рамки в 118 пикселей это порядка **0.05**. Отсюда
и весь предыдущий провал - "разумные" значения вроде 1.5 уносили модель на
двадцать ширин рамки вправо, и увидеть её можно было, только скрутив это число
почти в ноль, где камера уже стояла внутри модели. Симптом ("видно только
вплотную") при этом читался как неверная дистанция, хотя перепутана была ось.

**Как кадрируем сейчас.** Размер задаёт `SetModelScale`, а не глубина:
`k = min(w, h) / габарит * fill`, где габарит берётся из присланных сервером
`radius`/`height`. Модель ставится в центр рамки, с опусканием на половину
высоты - начало координат у пропов в основании, иначе в центре кадра оказались
бы их ноги. У такого способа два следствия: настройка не зависит ни от размера
рамки, ни от разрешения экрана, и большое превью автоматически показывает то же
самое крупнее, потому что `w`/`h` у него больше.

**Ракурс - три четверти, а не анфас.** У сундука или ящика в лоб видна одна
плоская грань, и две похожие модели так не различить. Поворот по умолчанию -
около 40 градусов.

**Осей вращения у клиента меньше, чем хочется.** На 3.3.5 у `Model` есть только
`SetFacing` - рыскание вокруг вертикали. `SetPitch` и `SetRoll` в документации
виджета описаны, но появились в более поздних клиентах, а своей камеры у пропов
нет, так что и `SetCamera` не выручает. Поэтому наличие осей определяется **у
самого виджета**, а не по версии игры:

```lua
local HAS_PITCH = type(preview.SetPitch) == "function"
local HAS_ROLL = type(preview.SetRoll) == "function"
```

Чего нет - имитируется перспективой: объект, смещённый от оси камеры, виден под
углом, поэтому "наклон" без `SetPitch` отрабатывается вертикальным сдвигом
модели в рамке. Полноценный наклон это не заменяет, но вертикальное движение
мыши перестаёт быть мёртвым, и на клиенте, где `SetPitch` есть, тот же жест
начинает работать по-настоящему без единой правки.

Левая кнопка крутит по всем доступным осям: вбок - рыскание, вверх-вниз -
наклон, с `Shift` вбок - крен. Правая двигает модель в кадре. Автовращение
трогает только рыскание, чтобы подобранные наклон и крен не сбивались.

**Позиция модели не вычисляется, а калибруется - и это осознанное отступление.**

Три попытки вывести её из документации дали три разных неверных результата:
сначала перепутанные оси, потом орбита при вращении, потом вид сверху вместо
вида в лицо. Вывод: сопоставление аргументов `SetPosition` с экраном на этом
клиенте не такое, как описано, и выводить его из текста бесполезно.

Поэтому три аргумента отданы наружу как есть, в долях рамки (`px`, `py`, `pz`),
видны в подписи и правятся мышью: правой (или `Ctrl`+левой) - первые два,
`Shift`+колесо - третий. `Shift`+клик по "Сброс" печатает подобранную тройку в
чат, чтобы её можно было зашить константой. Настраивается один раз на весь
каталог: это свойство камеры виджета, а не конкретной модели.

Никаких поправок на угол в позиции больше нет. Если модель при вращении ходит
по кругу - значит `SetFacing` крутит её вокруг оси сцены, а не своей, и лечится
это подбором позиции, а не формулой. Прежняя компенсация на центр габаритов
(из `GameObjectDisplayInfo`, поля `minX..maxZ`) убрана: она исправляла смещение
в единицах модели, тогда как настоящая причина была в самой позиции. Сервер
центр всё ещё присылает - пригодится, если до формулы всё-таки дойдёт.

**Ось вращения одна** - `SetFacing` вокруг вертикали, больше клиент 3.3.5
ничего не даёт. Вертикаль мыши работает только там, где есть настоящий
`SetPitch` (определяется у виджета в рантайме). Подделывать наклон смещением
модели по вертикали - плохая идея, проверено: модель начинала ездить
вверх-вниз вместо наклона и маскировала настоящие дефекты кадра.

**Урок для следующего раза.** Три круга догадок стоили дороже, чем стоила бы
калибровка с первого раза. Признак, по которому это надо было понять раньше:
документация даёт одну версию осей, а наблюдаемое поведение - другую, и обе
непроверяемы без запуска. В такой ситуации правильный ход - вынести неизвестные
в интерфейс и померить, а не выводить.

### Границы

* Объекты **у каждого админа свои**: чужие он не видит в `.rc go list` и не
  двигает.
* Лимит `RemoteControl.MaxObjects` (по умолчанию 50) считает только
  незакреплённые: закреплённые из-под модуля уходят.
* Всё состояние в памяти. Таблицы у модуля по-прежнему нет - осознанно, см. §3.4.

## 10. Открытые вопросы

* Иконки предметов в Phase 1: `GetItemInfo(id)` для кастомных предметов вернёт nil
  до попадания в клиентский кэш. Варианты - ретрай через 0.5 с либо отдача
  `displayid` с сервера. Решать при реализации поиска.
* Нужна ли история действий с выборкой (таблица в БД) или хватает лога.
* Лут расставленных объектов - следующий шаг Phase 2a. Сундук (`type = 3`)
  сейчас берёт лут из своего `gameobject_template`; своя таблица лута под
  «мировые предметы» появится, когда будет понятно, чем их наполнять.
* Масштаб (`OBJECT_FIELD_SCALE_X`) на закреплённом объекте не сохраняется:
  в таблице `gameobject` поля масштаба нет. Пока это принято как есть -
  закрепляют обычно то, что уже подогнали размером по умолчанию.
* Совсем без моргания призрак получился бы, если носителем сделать **криттера**:
  юниты двигаются плавно (`SMSG_MONSTER_MOVE`) и умеют быть полупрозрачными
  через невидимость-с-детектом. Но модели геймобъектов лежат в
  `GameObjectDisplayInfo.dbc`, а модели существ - в
  `CreatureDisplayInfo`/`CreatureModelData`, так что под каждый проп нужна своя
  пара строк в клиентском MPQ. Для дюжины избранных - реально, для каталога на
  30k - нет. Отложено до появления спроса.
* Побочное наблюдение при разборе ядра: `WeatherScript` в
  mod-environmental-effects фактически мёртв (database-bound,
  `game_weather.ScriptName` не проставлен). На поведение не влияет - там есть
  дублирующий реконсайл по зоне при смене зоны/области, - но стоит либо убрать,
  либо перевести на `ALEScript`.
