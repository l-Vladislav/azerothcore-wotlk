## What the SQL does

Auto-generated by `modules/mod-gear-ascension/scripts/gear-ascension-gen-extra.ps1`.
Adds two new locked groups to the Gear Ascension upgrade pool WITHOUT touching the existing pool (entries 300001-345833):

| Group | Base count | Copy count | Entry range |
|---|---|---|---|
| CRAFT: Q1-3 profession-crafted gear (itemset=0) | 639 | 1,092 | 345841-356762 (subset) |
| SET: Q1-3 set items (itemset<>0) | 454 | 634 | 345841-356762 (subset) |
| **Total** | **1,093** | **1,726** | **345841-356762** |

Per-base ID formula: `new_entry = 300000 + baseIndex*10 + step` (step 1..3, CRAFT_BI_START=4584).

Each base gets:
- 1-3 `item_template` rows (tier copies at +10% stats per step)
- 1-3 `item_upgrade_chain` rows (upgrade edges with next/prev pointers)
- 1-3 `item_template_locale` rows (ruRU names with PREFIX+SUFFIX naming from DESIGN.md sec 10)

The SQL is idempotent: it DELETEs its own range (by `origin_entry` list and entry range) before re-inserting, so re-running is safe.

**Item.dbc note:** The patched Item.dbc (56,465 records) is ALREADY deployed to the shared volume
`azerothcore-wotlk_ac-client-data-v2` (mounted at `/data/dbc/Item.dbc`). No separate DBC deploy step
is needed. The live worldserver will pick it up on its next restart (it is a harmless superset until
then — entries 345841-356762 simply have no item_template rows on live yet). In-volume backup:
`/data/dbc/Item.dbc.bak-pre-craftset`. Host backup: `.claude/dbc/_volume_Item.dbc.pre_craftset.bak`.

**ItemSet.dbc note:** ItemSet.dbc is client-only for display. The server counts set bonuses via
`item_template.itemset` field (verified in `Item.cpp::AddItemsSetItem`). No server-side ItemSet.dbc
change is needed. Client MPQ already updated by owner.

**No C++ rebuild required:** This is a pure data migration. The existing mod-gear-ascension binary
already handles these new entries via the same code path as Phase 1/2.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Large SQL (52,792 lines, ~3,452 INSERT+UPDATE statements for 1,726 copies) | LOW | File-redirect via `docker exec -i` handles large inputs fine; MySQL will not time out under local Docker. Allow ~2-5 minutes for apply. |
| Existing Phase 1/2 pool (300001-345833) untouched | NONE | Idempotency DELETEs are scoped to `origin_entry IN (1093 specific IDs)` and `entry BETWEEN 345841 AND 356762`. Existing rows are never touched. |
| Item.dbc already deployed (superset) | NONE | Live worldserver reads what it needs from item_template; extra DBC entries for unknown items are silently ignored until the SQL applies. On restart after SQL, all 56,410 templates load with 0 errors. |
| Re-run safety | NONE | DELETE-before-INSERT pattern makes the SQL fully idempotent. |
| No character data risk | NONE | Only acore_world is touched. acore_characters is unchanged. No character inventory contains entries 345841+ (they don't exist yet). |
| Worldserver restart window | LOW | The restart is the only player-visible interruption. Schedule for low-traffic window. |

## Rollback procedure

See `rollback.ps1` in this package directory.

Two rollback options:
1. **Surgical DELETE** (fast, no restore needed): Removes only the new rows. Existing pool and character data are untouched.
2. **Full snapshot restore** (slow, complete): Restores the full acore_world from the pre-deploy snapshot taken by apply.ps1.

Option 1 is preferred — it is faster (~30 seconds) and avoids any risk of losing concurrent writes to other acore_world tables. Option 2 is the fallback if Option 1 fails or if the snapshot is needed for other reasons.

The volume Item.dbc rollback is optional and only needed if the DBC itself is suspected broken (it was already deployed before this package, so reverting the SQL does not require reverting the DBC).
