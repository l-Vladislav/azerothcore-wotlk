# admin-panel

Центральный управляющий узел сервера: одна веб-панель, из которой видно
состояние сервера, редактируется контент модулей и ведутся баги и идеи.

Страницы:

| Адрес | Что там |
| --- | --- |
| `/` | статус (БД, SOAP, счётчики) + плитки модулей |
| `/board.html` | канбан-доска: баги, идеи, задачи |
| `/envfx.html` | редактор **mod-environmental-effects** — правила зон и глобальный пул |
| `/weather.html` | погода **mod-advanced-weather** — состояние зон, ручная погода, закрепление, связи зон, фронты на карте |
| `/weather-settings.html` | настройки того же модуля — режиссёр, циклоны, все числа без правки конфига |
| `/italents.html` | редактор **mod-item-talents** — категории, пулы перков, пороги |
| `/spells.html` | мастерская спеллов — правка `spell_dbc` |
| `/dex.html` | каталог спеллов — все ~55 000, только чтение |
| `/users.html` | люди и доступ: профили, роли, ссылки-приглашения (владелец) |
| `/audit.html` | журнал изменений: кто, когда, что и в каком модуле (владелец) |
| `/login.html` | вход |
| `/join.html` | регистрация по ссылке-приглашению |
| `/api/docs` | схема API |

Редакторов модулей три — эффекты окружения, таланты предметов и погода.
Остальные модули на главной значатся как «редактора пока нет», но карточки на
доске под них уже можно заводить.

Редактор талантов правит то, что раньше было зашито в C++ и в conf:
какие предметы попадают в какую категорию, из каких вариантов состоит меню
ряда (10 вариантов, роллится 3), персональные пулы конкретных эпиков и
пороги убийств по (качество, ilvl). Применяется на живом PTR командой
`.itemtalent reload` — рестарт не нужен.

Страница погоды устроена иначе всех остальных: своей таблицы у неё нет. Погода
живёт в памяти worldserver'а, поэтому панель разговаривает с ним по SOAP
командами `.aw` из mod-advanced-weather и разбирает ответы `AW:ZONE:...`.
Отсюда автообновление раз в 15 секунд. Игроки на погоду не влияют: режиссёр
ведёт все зоны с климатом независимо от того, стоит ли там кто-нибудь, а
счётчик живых в правой колонке — справка «кто это сейчас видит», не более.

Одно исключение из «своей таблицы нет» всё же появилось — связи зон
(`mod_advanced_weather_zone_link`). Это не живое состояние, а настройка: у
зоны-источника перечислены соседи и сила связи в процентах, и погода переезжает
к ним с ослаблением — 100% отдаёт ту же самую, 49% превращает грозу в обычный
дождь. Панель правит таблицу напрямую и сразу шлёт `.aw linkreload`, так что
рестарт не нужен. В редакторе зоны видно оба списка: исходящие связи правятся,
входящие показаны для чтения (они принадлежат соседу) — и у каждой подписано,
во что превратится сегодняшняя погода источника. Лестница «гроза → ливень →
дождь → морось» продублирована в `weather.LADDERS` ради этого предпросмотра;
решение принимает сервер, так что расхождение испортит подсказку, а не погоду.

Список зон там курируемый (`weather.CONTINENTS`), а не весь `AreaTable`: 74 зоны
под открытым небом, разбитые по четырём континентам. Подземелья, рейды, арены,
моря и «НЕ ИСПОЛЬЗУЕТСЯ»-заглушки убраны — поставить погоду в них можно, увидеть
нельзя. Группировка географическая, а не по MapID: Кель'Талас и Остров Лазурной
Дымки лежат на карте Запределья, но показаны там, где их ищет человек. Зона вне
списка, которую всё-таки ведёт режиссёр, попадает в группу «Прочее» — иначе её
нельзя было бы отпустить.

### Карта погоды

Над редактором зоны лежит карта континента, на которой погода видна целиком:
зона светится цветом своей группы (дождь синий, снег белый, песчаная буря
песочная, особые состояния фиолетовые), плотность свечения даёт силу, клик
выбирает зону — тот же выбор, что и в списке слева. Границ у зон нет
намеренно: любая обводка спорит с рисунком карты, поэтому каждая зона — пятно
света из своего центра (радиальный градиент, радиус по габаритам зоны),
уходящее в ноль к краям. Выбранная зона просто светится плотнее; яркость
задаётся в самом градиенте, а не CSS-фильтром — на почти белом снеге фильтр не
виден. Закреплённую вручную выдаёт золотая подпись. Города подписаны точкой, а
не именем, иначе подписи налезают друг на друга. Континент переключается вкладками над картой:
Восточные королевства и Калимдор. Выбор зоны в списке слева сам перелистывает
карту на нужный континент — но только в момент выбора: проверка на каждой
перерисовке делала вкладки бесполезными, страница тут же возвращалась к
континенту выбранной зоны (перерисовка идёт ещё и по таймеру, раз в 15 секунд).
Если открыта не та карта, где живёт выбранная зона, в её плашке появляется
кнопка «показать: <континент>», а для континента без файлов карты (Запределье,
Нордскол) — честная подпись «карта не собрана».

Вдоль правого края карты стоит полоса со всей погодой выбранной зоны: кнопки
состояний небольшими квадратами с иконкой (38 px, название всплывает при
наведении;
подсвечена та погода, что в зоне СТОИТ, а не набранная в редакторе — полоса
показывает мир, а не черновик), под ними сила с удержанием и «Применить /
Закрепить / Вернуть режиссёру». Иконки нарисованы инлайновым SVG прямо в
`weather.js`: у панели принцип «без изображений и вебшрифтов», а SVG вдобавок
красится `currentColor` — активная кнопка золотая, остальные приглушены.
Различают состояния не рисунком, а счётом: одна капля — морось, три — ливень,
у порченых осадков туча залита. Клик по состоянию ставит погоду сразу, с теми
силой и удержанием, что набраны тут же — задавать их в другой колонке значило
бы жать кнопку вслепую. В редакторе всего этого больше нет; весь набор
возвращается туда сам, если файлы карты не собраны и управлять иначе нечем.

Сила — плотность осадков (`grade`), ползунок начинается с 30%: ниже 27% клиент
рисует ясное небо независимо от присланного состояния. Удержание — сколько
минут ручная погода держится до возврата зоны режиссёру; 0 берёт
`AdvancedWeather.ManualHoldMinutes` из конфига модуля.

Слева от полосы, в верхнем углу карты, стоят две кнопки. Первая — подписи зон:
на плотных участках (Кель'Талас, дренейские острова) названия закрывают ровно
то, что человек пришёл разглядывать. Прячутся только подписи — точки городов
остаются, они не название, а единственная отметка того, что зона там есть.
Состояние помнится в `localStorage`.

Переключателя режиссёра тут больше нет — он уехал на страницу настроек, где
рядом с ним встали остальные её ручки. Осталась подпись в шапке: она же ссылка
туда, потому что прочитав «режиссёр выключен», человек хочет включить его, а
не искать, где эта кнопка живёт.

Поверх карты, под свечением зон, идут **фронты** — не кружки, а циклоны:
рваная облачная пелена, глаз-прояснение в середине, логарифмическая спираль
рукавов вокруг него, пунктирная кромка и стрелка курса.

Сам вихрь — **готовая рисованная текстура** `app/static/cyclone.png` (320x320,
она в репозитории). До неё тут побывали процедурный фрактальный шум и
спутниковый снимок урагана: шум давал облака, но не давал спирали, а снимок
был серый, спорил с рисованной картой и его пришлось бы перекрашивать.
Рисованный вихрь садится на карту как родной.

Перегенерировать из исходника — `scripts/make_cyclone_texture.py` (нужен
Pillow, в контейнере панели его нет, гоняется локально). Он режет квадрат по
границам непрозрачной части, а не по центру кадра, и уменьшает по
**предумноженной альфе**: обычный resize усредняет цвет вместе с прозрачными
пикселями, у вырезанных картинок они чёрные, и вокруг вихря появляется тёмный
ободок, которого в исходнике нет.

Прозрачность — 50%, и задаётся она в CSS (`.wmap-cyclone-texture`), а не в
самом файле: под фронтом должно быть видно, какая погода в зоне СТОИТ, иначе
карта под ним слепнет. Смешивание обычное, не `screen`: у текстуры тёмные
полосы между рукавами несут форму, а `screen` съедает всё тёмное и оставляет
одно свечение.

Своих рукавов поверх текстуры панель не рисует: на ней они уже есть, и вторая,
нарисованная спираль читалась бы как два вихря в одном месте. Кромка фронта,
окружность глаза и стрелка курса остаются — они и есть точные, их размеры
приходят из протокола, и красятся они в цвет семейства, так что цветовая
подсказка на карте никуда не делась.

### Страница настроек

`/weather-settings.html` ничего о модуле не знает заранее: реестр настроек
живёт в C++, приезжает по `.aw cfg` и рисует поля по границам, которые сервер
же и прислал. Добавили строку в реестр — поле появилось здесь само; панель
добавляет от себя только человеческое имя, пояснение и группу.

Наверху отдельно и крупно — сам режиссёр: пока он выключен, вся страница ниже
украшение, и это должно быть видно, не читая. Дальше группы: «Циклоны»,
«Одиночные броски» (работают, только когда циклоны выключены), «Связи зон».
Переопределённое из базы помечено золотой кромкой и кнопкой «сбросить» —
по странице сразу видно, что именно уехало от конфига, и чем это вернуть.
Числовые поля пишутся по Enter и по уходу из поля, а не на каждое нажатие:
иначе «3500» по дороге успело бы съездить в «3» и смести все фронты.

Внизу — живые фронты карточками: семейство, радиус, ступень в ядре, скорость,
сколько зон под ним и через сколько уйдёт. Это не настройка, а то, что из
настроек получилось, — по ним и видно, сработала ли правка. Кнопка
«Перезапустить фронты» (`.aw cycreset`) сметает их и запускает новые, если
ждать полчаса не хочется.

На worldserver'е, собранном без `.aw cfg`, страница честно говорит, что её
нечем наполнить, вместо того чтобы рисовать пустые поля. Протокол при этом не
поднимали: строка `AW:ZONE` не менялась, а новые команды панель определяет по
ответу.

В левом нижнем углу карты, поверх открытого моря, лежит плашка «сейчас на
континенте»: она же обозначения, она же счётчик. Цветная точка объясняет карту,
число рядом говорит, сколько зон под этой погодой; строки с нулём остаются
(иначе пропавший «снег» пришлось бы вспоминать), а «не ведётся» показывается
только когда такие зоны есть.

Раскладка страницы — три колонки: список зон, карта, работа с зоной. Состояние выбранной зоны написано на самой карте, слева вверху: имя, id,
погода с силой, источник со сроком, игроки. Континента и числа связей там нет —
первое видно по карте, второе живёт в редакторе связей, где им и занимаются. В
правой колонке остаётся управление: сила и удержание, «Применить / Закрепить /
Вернуть режиссёру», связи, — и в самом низу климат зоны по сезонам с пометкой у
сегодняшнего. Климат последним намеренно: это справка о том, из чего режиссёр
выбирает, а не ежедневное управление; пояснение к таблице спрятано под знаком
вопроса, чтобы мелкий текст не читался как её часть. Под картой не осталось ничего: там редактор занимал вторую
половину экрана, до которой надо было доскроллить, а карта в это время упиралась
в собственный потолок ширины.

Страница помещается в окно целиком: скроллятся колонки, а не она сама. Высота
шапки при этом НЕ вычитается числом — так было, и это стоило ровно пяти
пикселей вертикального скролла на любом размере окна, потому что остальная
вёрстка считает шапку 48 px, а на деле она 53. Теперь колонки забирают остаток
через flex, а карта дополнительно ограничена по высоте окна (лист 3:2, иначе на
широком экране он вылезал за нижний край).

Колонки резиновые (`clamp`), и «Скрыть список» в шапке отдаёт освободившееся
место карте и правой колонке, а не пустоте. Ниже 1150 px они перестают ужиматься
и встают друг под друга: список сверху, карта во всю ширину, работа с зоной под
ней. Карта тянется до 1360 px — выше родных 1002 px лист мылится, но на широком
экране это лучше, чем резкая картинка с пустым полем рядом. Состояние обеих
кнопок помнится в `localStorage`.

Двух файлов карты в репозитории нет и не будет: подложка — арт Blizzard.
Собираются они локально и один раз:

```powershell
# оба континента разом; -Continent ek|kalimdor соберёт один
tools/admin-panel/scripts/build-map-assets.ps1 -Client "E:\...\World of Warcraft"
docker compose --profile ptr up -d --build ac-admin-panel
```

Названия у клиента и у сервера расходятся: папка арта Восточных королевств
зовётся `Azeroth`, а MapID у них 0 — соответствие ключей панели, папок и карт
лежит в самом скрипте.

Половинки берутся из разных мест, и обе — из того, что уже есть на машине:

* **подложка** — 12 тайлов BLP из клиентского MPQ. У локализованного клиента
  они лежат в `Data/ruRU/locale-ruRU.MPQ`, а не в `common.MPQ`: на карте
  выгравированы названия, поэтому она переведена. Двенадцать тайлов 256x256
  складываются в лист 1024x768, из которого клиент показывает верхние
  1002x668 — только их и берём (`scripts/gen_map_art.py`).
* **контуры зон** — сетка area-id из серверных `maps/*.map`, которые
  worldserver и так грузит. Ячейка сетки — 33.33 ярда, то есть меньше пикселя
  на карте такого размера, поэтому границы получаются настоящие, а не
  прямоугольники из `WorldMapArea.dbc` (те перекрываются и с берегом не
  совпадают). Море отбрасывается, иначе каждая прибрежная зона рисуется плитой
  воды до края карты (`scripts/gen_zone_geometry.py`).

  Море — это НЕ флаг океана сам по себе. Тельдрассил стоит над океанскими
  ячейками, и флага хватило, чтобы выесть остров в кольцо береговой линии.
  Ячейка считается морем, только если рельеф под ней лежит ниже поверхности
  воды больше чем на пару ярдов; для этого читается ещё и карта высот.

Сходятся они не по подгонке: континентальная строка `WorldMapArea.dbc` для
Калимдора даёт ровно 1104x736 ячеек с соотношением 1.5 — то самое, что у
картинки 1002x668. Если однажды не сойдётся, значит поменялась математика, а не
арт. Генератор контуров запускается внутри контейнера панели: том
`ac-client-data-v2` с `maps/` примонтирован только туда.

Дренейские острова — Азурмист, Кровавая Дымка и Экзодар — физически лежат на
карте 530 рядом с Запредельем, но нарисованы на листе Калимдора; Кель'Талас
оттуда же приезжает на лист Восточных королевств. Клиент делает это через
`WorldMapTransforms.dbc`: строка переносит угол карты 530 на другую карту с
фиксированным сдвигом. Генератор читает ту же таблицу, поэтому у этих зон есть
контуры, а не только арт.

Что всё-таки не попало на лист континента, показано чипами в правой колонке
(блок прячется, когда пуст). На Восточных королевствах туда попадают Стальгорн,
Подгород и Дун Альгаз — они внутри горы, а сетка area-id плоская: на их клетках
записана та зона, что лежит сверху.

Хиджал и Врата Ан'Киража, наоборот, есть на карте, но панель ими не
распоряжается — они серые и не кликаются.

Мастерская и каталог — про спеллы, но с разных сторон: мастерская правит те
несколько сотен, что мы авторим сами, каталог показывает всё, что вообще знает
сервер, и ничего не пишет.

## Оформление

Тема — «слегка WotLK»: тёмный камень, бронзовые рамки, золотые заголовки,
серифный шрифт из системного набора Windows. Цвета качества предметов
используются осмысленно, а не для красоты: приоритет карточки читается как
привычная лестница качества (серый → зелёный → фиолетовый → оранжевый).

Ни картинок, ни веб-шрифтов — всё на CSS-градиентах и одном inline-SVG
(стрелка у `<select>`), поэтому панель одинаково выглядит офлайн и в tailnet.
Единственная внешняя загрузка осталась прежней и необязательной — иконки
спеллов с CDN, см. раздел «Иконки».

Рядом лежит `app/static/style.hive.css` — альтернативная тема по образцу
hiveworkshop.com: почти чёрные плоские панели, янтарный `#f8b700`,
багрово-золотые кнопки, круглые металлические медальоны иконок, Segoe UI без
серифа. Переключиться:

```bash
cd app/static && cp style.hive.css style.css
cd ../../../.. && docker compose --profile ptr up -d --build ac-admin-panel
```

Обе темы держат один и тот же набор селекторов, так что смена файла ничего не
ломает — разметку и JS трогать не нужно.

## Люди, роли и доступ

Раньше панель знала одного оператора и один общий токен. Теперь у каждого свой
профиль, и «кто звонит» — настоящий ответ: им подписаны карточки на доске и
каждая строка журнала.

### Три роли

| Роль | Что может |
| --- | --- |
| смотрящий | читает всё и работает с доской: заводит баги, идеи и задачи, комментирует, двигает карточки |
| редактор | плюс редакторы модулей: погода, эффекты окружения, таланты предметов |
| владелец | плюс то, что тяжело откатить: мастерская спеллов, выгрузки в SQL и в клиент, сброс кэша — и раздача доступа |

Роли лестничные: проверка всегда «не ниже такой-то». Живёт она в одном месте —
`_role_dep()` в `app/main.py`, — и навешена на каждый эндпоинт: `Viewer`,
`Editor`, `Owner` в сигнатуре. Новый эндпоинт без такой зависимости просто не
получит вызывающего, так что забыть про доступ трудно.

Клиент ничего не прячет, кроме пунктов меню владельца: решает сервер, а отказ
приезжает читаемым тостом («Нужна роль «владелец» или выше; у тебя
«редактор»»). Это осознанный размен — прятать кнопки в шести редакторах значит
разойтись с сервером ровно в тот день, когда права поменяются.

### Приглашения

Публичной регистрации нет. Владелец на `/users.html` жмёт «Пригласить»,
выбирает роль, срок и число использований — панель выдаёт ссылку вида
`http://<хост>:8091/join.html#<секрет>`. Пришедший по ней сам придумывает логин
и пароль и попадает сразу в ту роль, что несёт ссылка.

Несколько решений, которые стоит знать:

- **Секрет живёт в якоре ссылки** (`#`), а не в query. Якорь не уходит на
  сервер в строке запроса и не утекает в `Referer` — приглашение не оседает в
  логах. После успешной регистрации страница вычищает его и из истории вкладки.
- **В базе лежит только SHA-256** — и от приглашения, и от сессии. Утёкшая
  строка таблицы не воспроизводится как доступ. Обратная сторона: показанную
  один раз ссылку панель повторить не может, только выдать новую.
- **Ссылка одноразовая и со сроком** (по умолчанию 72 часа). Расход считается
  условным `UPDATE ... WHERE uses < max_uses`, так что двое, открывшие одну
  ссылку одновременно, не пройдут оба.
- **Адрес берётся из запроса.** Панель не знает своего внешнего адреса, поэтому
  ссылка строится от того хоста, через который на неё смотрит владелец. Если
  открыть панель как `127.0.0.1`, ссылка получится с `127.0.0.1` — открывай её
  по tailnet-адресу, тогда и приглашение выйдет рабочим.

### Пароли и сессии

Пароль хранится через `hashlib.scrypt` из стандартной библиотеки — не argon2 и
не bcrypt. Тащить в образ нативную зависимость ради горстки аккаунтов внутри
tailnet — размен хуже, чем стандартный KDF, который и так memory-hard.

Сессия — кука `ac_admin_sid`, HttpOnly, 30 дней, срок сдвигается при каждом
запросе. Смена роли, отключение профиля и смена пароля закрывают все его
сессии: иначе правка вступала бы в силу только когда человек сам решит
перезайти. Куки без `Secure` — панель отдаётся по обычному HTTP в tailnet, и
`Secure`-кука просто не сохранилась бы; если увести панель за
`tailscale serve`, флаг надо будет включить (`_set_session()` в `main.py`).

### Общий токен никуда не делся

`ADMIN_PANEL_TOKEN` работает как раньше и даёт права владельца. Он остался
затем, что кто-то должен выдать первое приглашение, и как запасной ход, если с
таблицей сессий что-то случится. Правки под ним подписаны в журнале как
`root` — по ним не видно, кто из владельцев их сделал, так что повседневно
лучше ходить профилем.

Пока профилей нет, страница входа сама открывает эту дверь и объясняет, что
происходит.

### Последний владелец

Понизить или отключить последнего активного владельца панель не даёт, как и
удалить его: это единственная ошибка на этой странице, у которой нет
внутрипанельного лекарства. Себя понизить или удалить нельзя вовсе — попроси
другого владельца.

## Журнал изменений

`/audit.html` — кто, когда, в каком модуле и что именно отправил. Только для
владельца, только чтение, новые записи сверху. Фильтры: раздел, человек,
подстрока, «только ошибки».

Пишется он **одним перехватчиком** (`audit_changes` в `main.py`), а не вызовом
внутри каждого редактора. Это и есть главное решение: изменяющих эндпоинтов
под сорок и с каждым модулем их больше, а журнал, который надо не забыть
позвать, — это журнал с дырами. Записывается всё, что не GET и живёт под
`/api/`, поэтому новый эндпоинт попадает в журнал в день, когда написан.
Чтения не пишутся вовсе, вход и выход — тоже (они ничего не меняют и завалили
бы ленту).

`audit.RULES` превращает метод и путь в человеческую строку («Погода · зона
1519 · выставлена погода вручную»). Путь, которого в таблице нет, всё равно
даёт запись — просто с техническим `PUT /api/что-то`: лучше сухая строка, чем
молчание.

Что лежит в записи — **отправленное состояние, а не разница** с тем, что было.
Редакторы шлют объект целиком, так что тело отвечает на «во что он это
превратил», но не на «что там было до». Считать «до» значило бы читать перед
записью в каждом эндпоинте — ровно та связность, которой этот перехватчик и
избегает. Предыдущее значение лежит строкой выше в том же журнале.

Отказы записываются наравне с успехами: строка с `ok=0` и кодом видна в ленте
красным, а фильтр «только ошибки» показывает попытки залезть не в свою роль.

Пароли и токены приглашений заменяются на «скрыто» до того, как тело попадёт в
таблицу, — журнал читает любой владелец.

## Границы

- **Редакторы модулей — только PTR.** `app/config.py` отказывается стартовать,
  если `ADMIN_DB_NAME` не заканчивается на `_ptr`. Обойти можно только
  `ADMIN_ALLOW_NON_PTR=1`.
- **Каталог спеллов только читает.** У `/dex.html` нет ни одного пути записи:
  том с клиентскими DBC примонтирован `:ro`, а правки идут через мастерскую.
- **Таблицы на запись** в игровой БД — `mod_environmental_effects`
  (редактор зон), `spell_dbc` (мастерская) и восемь `item_talent_*`
  (редактор талантов:
  `category`, `category_rule`, `def`, `row_cfg`, `item_def`, `item_cfg`,
  `kill_curve`, `perk_library`). Всё остальное (`item_template`,
  `game_weather`, `AreaTable.csv`, `client_manifest.csv`, клиентские DBC)
  читается.
- **Панельные данные живут отдельно** — в собственной схеме `acore_admin`
  (`ADMIN_BOARD_DB_NAME`), которая создаётся при первом запуске: доска, люди и
  журнал. Это не игровые данные, и откат PTR-снапшота не должен стирать ни
  заведённые баги, ни профили, ни историю правок. Поэтому `app/paneldb.py` не
  ходит через `db.connect()` — у того PTR-гард, который `acore_admin` отверг бы
  по построению.
- **Доступ решается на сервере.** `_role_dep()` в `app/main.py` — единственная
  функция, которая решает «кто звонит и хватает ли ему прав»; фронт только
  честно подписывает результат.

## Запуск

```bash
# .env (рядом с docker-compose.yml)
ADMIN_PANEL_TOKEN=<длинная случайная строка>
ADMIN_SOAP_USER=<аккаунт acore_auth с gmlevel >= 3>
ADMIN_SOAP_PASS=<его пароль>
ADMIN_PANEL_BIND=127.0.0.1        # или tailnet-адрес

docker compose --profile ptr up -d --build ac-admin-panel
```

Открыть панель — она отправит на `/login.html`. Профилей ещё нет, поэтому
страница сама разворачивает «Войти общим токеном»: это `ADMIN_PANEL_TOKEN`, он
даёт права владельца. Дальше — «Люди» в шапке, «Пригласить», и ссылка на
себя же, чтобы завести нормальный профиль.

Чтобы позвать друзей по сети, панель должна слушать не только локалхост:

```bash
ADMIN_PANEL_BIND=100.101.76.86     # tailnet-адрес машины
```

Ссылка-приглашение строится от того адреса, по которому открыта панель, так
что выдавать её надо с tailnet-адреса, а не с `127.0.0.1`.

Статика запечена в образ, так что после правок в `app/` нужен пересбор
(`up -d --build`), а не только рестарт.

### Предпосылки на стороне сервера

1. `env/dist/etc-ptr/worldserver.conf`: `SOAP.Enabled = 1`, `SOAP.IP = "0.0.0.0"`
   (уже выставлено). Порт 7878 внутри контейнера, 7880 на хосте.
2. PTR-worldserver запущен: `docker compose --profile ptr up -d ac-worldserver-ptr`.
3. Аккаунт для SOAP: `acore_auth.account_access.gmlevel >= 3`
   (`ACSoap.cpp` требует `SEC_ADMINISTRATOR`).

Без SOAP панель остаётся рабочей — правки уходят в БД, но применяются только
после ручного `.reload config` или рестарта. Доске SOAP не нужен вовсе.

## Доска

Пять колонок: `backlog → todo → doing → review → done`. Карточка это баг
(🐞), идея (💡) или задача (🔧); у неё есть приоритет, модуль, теги,
исполнитель и комментарии.

- Перетаскивание — обычный HTML5 drag-and-drop. Дроп шлёт один
  `POST /api/board/cards/{id}/move` с колонкой и индексом, сервер отвечает
  всей доской, поэтому клиент и БД не расходятся.
- «В архив» — мягкое удаление (`archived = 1`), кнопка **Архив** в шапке
  показывает архив и позволяет вернуть карточку. Насовсем — только через API
  (`DELETE ...?hard=true`).
- С главной страницы плитка модуля ведёт на доску с уже выставленным
  фильтром (`/board.html?module=<id>`), а «＋ карточка» сразу открывает форму.

Схема (`board_card`, `board_comment`) описана в `app/board.py:SCHEMA` и
создаётся кодом — миграции в `data/sql/updates/` для неё не нужны, это не
игровая БД.

## Добавить модуль на главную

1. Запись в `app/registry.py` — `status="planned"` достаточно, чтобы под модуль
   можно было заводить карточки.
2. Когда появится редактор: страница в `app/static/`, её имя в `PAGES`
   (`app/main.py`), `status="ready"` и `url` в реестре.

Форма, которую стоит повторять для нового редактора, — `app/envfx.py`: файл на
модуль, в нём схема таблицы, `validate()`, кодирующая то, что реально читает
C++, и транзакционная замена вроде `save_zone()`.

## Что делает кнопка (эффекты окружения)

| Кнопка | Действие |
| --- | --- |
| **Применить на PTR** | валидация → запись правил зоны в одной транзакции → `.reload config` по SOAP |
| **Перезагрузить правила** | только `.reload config` |
| **Экспорт в SQL** | перезаписывает `data/sql/updates/pending_db_world/mod_env_effects_v2_seed.sql` текущим состоянием таблицы (атомарно) |

Экспорт — это то, что делает панель источником правды: состояние живёт в БД, но
попадает в git. На live правила уезжают обычным deployment-package'ом, панель
сама к live не ходит.

## Валидация

Ошибки (блокируют сохранение, можно продавить «сохранить всё равно»):

- спелла нет в `spell_dbc` — сервер молча пропустит правило при загрузке;
- дубль спелла в одном пуле;
- отрицательный `zone_id`.

Предупреждения (не блокируют):

- id вне блоков модуля (`107000-107499` баффы, `107500-107799` дебаффы) или из
  чужого блока;
- `trigger_type` у баффа / `time_flag` у дебаффа — ядро их игнорирует;
- больше трёх активных слотов **в одной корзине** (дебаффы считаются по
  триггеру, баффы — отдельно по «доступным днём» и «доступным ночью»: ротация
  выбирает внутри корзины, а не по всему пулу);
- все баффы «только днём» или все «только ночью» — с пометкой, закрывает ли
  дыру глобальный пул;
- погодный дебафф в зоне, которой нет в `game_weather` — не сработает никогда;
- триггеры «Туман», «Гроза», «Чёрный дождь», «Чёрный снег» — ядро таких
  состояний не генерирует, они сработают только если выставить погоду вручную;
- у зоны есть правило «Дождь», но ни у неё, ни в глобальном пуле нет правила
  «Гроза» / «Чёрный дождь» — в такую погоду дебаффа не будет вовсе (аналогично
  «Снег» → «Чёрный снег»).

## Глобальный пул (zone_id 0)

Первая строка в списке зон — не зона, а **умолчания для всех зон таблицы**.
Подставляются **по корзинам**: корзина — это один эффект (постоянные дебаффы,
дебаффы одной погоды, баффы, подходящие текущему времени суток). Если у зоны в
корзине нет ни одного своего правила, берутся глобальные; если есть хоть одно —
глобальные для этой корзины молчат. Смешения нет: свой дождевой пул зоны
перебивает глобальный дождевой целиком, но грозовой при этом всё равно
подставится из глобального.

Зона, у которой нет вообще ни одной строки, остаётся пустой: модуль по-прежнему
opt-in, глобальный пул закрывает дыры только в уже подключённых зонах.

С 2026-08-19 у каждой погоды **ровно один** триггер: гроза — не дождь, чёрный
дождь — не дождь, чёрный снег — не снег. Раньше грозовое правило конкурировало с
дождевым и проигрывало жребий в половине случаев; теперь редкая погода звучит
по-своему, а пробелы закрывает глобальный пул.

## Каталог спеллов

`/dex.html` отвечает на вопрос «что уже есть», в отличие от мастерской, которая
отвечает «что мы сделали сами». Он читает три источника и склеивает их в том же
порядке, что и worldserver в `LoadDBCStores`:

1. `/client-data/dbc/Spell.dbc` — 49 839 записей из тома `ac-client-data-v2`,
   ровно те байты, которые грузит PTR-сервер;
2. `acore_world_ptr.spell_dbc` — 5 262 строки, которые `LoadFromDB` кладёт
   поверх: часть переопределяет стоковые спеллы, часть добавляет новые;
3. `.claude/dbc/Spell.csv` и `Spell_custom.csv` — **только тексты**. Бинарные
   DBC извлечены из enUS-клиента, поэтому русские названия и описания берутся
   из ruRU-выгрузок, а `Spell_custom.csv` вдобавок хранит настоящий
   `SpellIconID` кастомных спеллов.

Отсюда три «источника» в фильтре и в бейдже карточки:

| Бейдж | Что значит |
| --- | --- |
| клиентский DBC | стоковый спелл, никем не тронут |
| изменён | строка есть и в DBC, и в `spell_dbc` — модуль её переписал |
| добавлен | строки нет в клиентском DBC, она существует только в БД |

Фильтры **Модуль** и **Пул ID** — те же диапазоны, что раздаёт мастерская
(`app/spells.py:BLOCKS`), поэтому «чей спелл» и «в каком диапазоне» здесь один
вопрос:

- **Модуль** перечисляет только модули **со своим диапазоном** (env-effects,
  familiars, item-talents, statbooster) — фильтровать по ID модуля без
  диапазона не по чему. В скобках — сколько спеллов каталога попадает в его
  диапазоны.
- **Пул ID** сужает до одного блока; список пулов ограничен выбранным модулем.
  Без модуля есть пункт «Все кастомные блоки» — всё, что мы завели сами
  (`block=*` в API).
- Под селектом видны сами границы (`103000-103099, занято 100 из 100`).
- Бейдж пула в карточке спелла кликабельный: показать весь пул того спелла,
  который уже нашёлся.

Счётчики считаются по самому каталогу, а не по `COUNT(*) FROM spell_dbc`: в
диапазон может попасть и стоковый спелл, переписанный модулем.

У «изменён» в карточке спелла появляется секция **Что меняет spell_dbc**:
поколоночный дифф `DBC → БД`. Это самый быстрый способ увидеть, что именно
правил модуль, не читая его SQL.

Индекс строится при первом запросе (~4 с, из них 3 — разбор `Spell.csv`) и
живёт в памяти; полная строка спелла достаётся из mmap по требованию. Запись в
`spell_dbc` из мастерской сбрасывает кэш (`spelldex.invalidate()`).

### Чтение DBC

`app/dbcfile.py` — маленькая читалка WDBC: mmap, распаковка поля по запросу,
явная раскладка колонок. Раскладка `Spell.dbc` сверена с
`.claude/dbc/Spell.csv` по именам колонок — 138 числовых колонок на выборке
спеллов сошлись до последнего значения.

Две вещи, которые стоят времени, если выводить их заново:

- поле DBC — всегда 4 байта, поэтому два `uint64` (маски стоек) занимают
  четыре поля: 234 поля в файле против 232 имён колонок;
- локализованная строка — 17 полей (16 смещений + маска), и **ruRU лежит в
  слоте 8**. Это и есть тот самый сдвиг «ruRU = enUS + 8», который вылезает во
  всех CSV-выгрузках.

### Справочники для мастерской

Поля `DurationIndex`, `CastingTimeIndex`, `RangeIndex` и `EffectRadiusIndex` —
не числа, а индексы в отдельных DBC. Одноимённые таблицы `spellduration_dbc`,
`spellcasttimes_dbc`, `spellrange_dbc`, `spellradius_dbc` в игровой БД **пусты**
(сервер читает файлы), поэтому `spells.refs()` берёт варианты из DBC и кладёт
строки из БД поверх — тем же порядком, что и ядро. Получается 130 длительностей,
70 времён каста, 64 дальности, 58 радиусов вместо одного значения.

Значения, которые стоит помнить (сверено по `SpellDuration.dbc`):

| Индекс | Длительность |
| --- | --- |
| 21 | постоянная (`-1`) |
| 5 | 5 минут |
| 9 | **30 секунд** |

Пару «9 = 5 минут» из старых заметок можно смело забыть — это 30 секунд.

### Что нужно примонтировать

```yaml
volumes:
  - ac-client-data-v2:/client-data:ro   # Spell.dbc и остальные справочники
  - ./.claude/dbc:/repo/.claude/dbc     # Spell.csv, Spell_custom.csv, SpellIcon_custom.csv
environment:
  ADMIN_DBC_DIR: /client-data/dbc
```

Без тома каталог честно скажет «недоступен», остальная панель работает как
раньше. Без `.claude/dbc` каталог останется английским.

## Модуль и пул ID

Каждый модуль владеет диапазоном ID в `spell_dbc` (`app/spells.py:BLOCKS`), а
новый спелл получает **первый свободный ID своего пула**. Поэтому у черновика
модуль и ID — одно решение, и панель показывает их вместе, в группе
«Панель: модуль, иконка, заметка» (она открыта сразу):

- **Модуль** — список из `app/registry.py`, то есть тот же, что на главной.
  Смена модуля у *нового* спелла переносит его в диапазон этого модуля;
  у модуля без своего диапазона черновик уходит в «Мастерскую» (109000-109999).
- **Пул ID** — сам диапазон, если у модуля их несколько (у фамильяров три, у
  талантов предметов тоже: `108000-108049` скрытые триггеры проков ряда 5,
  `108050-108099` их видимые эффекты, `108900-108999` ауры рядов 1-4). Под селектом — `ID 109003 · занято 3 из 1000 (109000-109999)`, где ID
  берётся живым запросом `GET /api/spells/next-id?block=<id>`, а не из кэша
  страницы.
- У **сохранённого** спелла пул только показывается: сменить его — значит
  сменить ID, то есть завести другой спелл (для этого есть «Копировать»).
- В окне **⧉ Копия** пул выбирается до копирования, там же видно, какой ID
  получит копия.

Канон списка — `app/spells.py:BLOCKS`, и он должен покрывать всё, что мы
авторим: диапазон без блока не виден ни в фильтре мастерской, ни в фильтре
каталога, то есть спеллов будто нет. Сверка `GROUP BY FLOOR(ID/100)` по
`spell_dbc` от 2026-08-19 нашла три таких дыры — оба пула проков ряда 5
mod-item-talents (86 спеллов), ночной дебафф окружения `108500` и
`105000` от mod-gear-ascension; все три теперь блоки. Намеренно не
размечены чужие ID: `91003` (апстрим AzerothCore) и `200100`
(апстримный mod-transmog).

## Копия существующего спелла

Самый быстрый способ завести новый спелл — взять готовый. Копируются **все**
поля, кроме названия (`Name_Lang_ruRU` / `Name_Lang_enUS`): два спелла с
одинаковым именем неразличимы ни в тултипе, ни в боевом логе, ни в списке
мастерской.

Три входа:

| Откуда | Что делает |
| --- | --- |
| **⧉ Копия** в шапке мастерской | поиск по всему каталогу → выбор источника |
| **Копировать** в карточке открытого спелла | копия текущего |
| **Копировать в мастерскую** в каталоге | `/spells.html?clone=<id>` |

Источником может быть что угодно: свой спелл, стоковый спелл Blizzard или
стоковый, переписанный модулем. Поля берутся из того же слияния, что показывает
каталог (`DBC → spell_dbc`), русские тексты — из `Spell.csv`, иконка — из
`spell_meta` / `Spell_custom.csv` / `SpellIcon.dbc`.

`GET /api/spells/clone/{id}?block=workshop` **ничего не пишет**: он отдаёт
черновик с уже выданным свободным ID, а сохраняет обычный `POST /api/spells` —
то есть копия проходит ту же валидацию, что и спелл, набранный руками.

Черновик может вернуть предупреждения:

- у стокового источника — напоминание, что скрипты ядра, привязанные к его ID,
  на копию не перейдут (копируются только поля DBC);
- поля, которых нет в каталоге полей, — в копии они останутся нулевыми;
- дробные значения в целочисленных колонках, если такие попались.

### Что именно копируется (сверено по колонкам)

Каталог полей закрывает **все функциональные колонки** `spell_dbc`: 234 колонки
таблицы = 171 в белом списке панели (`ID` + 170 редактируемых) + 63, которые
никому не нужны. Сверено против `information_schema` и клиентского `Spell.dbc`:

| Колонки | Статус |
| --- | --- |
| 170 боевых (эффекты, атрибуты, тайминги, требования, реагенты) + `ID` | копируются |
| 57 колонок других локалей (`*_Lang_deDE` и т.п.) | не трогаем: панель ведёт ru/en |
| 4 маски локалей (`Name_Lang_Mask` и т.п.) | всегда `0`, в том числе у всех строк модулей |
| `unk_320_2`, `unk_320_3` | старшие 32 бита `ShapeshiftMask`/`ShapeshiftExclude`; `0` во всех 5 262 строках БД, и ни один стоковый спелл не выходит за 32 бита |

Две вещи, которые стоило проверить и которые оказались верны:

- **порядок колонок таблицы совпадает с порядком полей в DBC** (166 к 166 после
  разворачивания двух `uint64` в пары `int`). Это важно, потому что панель
  пишет по именам, а `DBCStorage::LoadFromDB` читает по позициям. Косвенное
  подтверждение: строки модулей, переписывающие стоковые спеллы, отличаются от
  файла в 1-5 колонках из 141, а не во всех;
- **единственное расхождение в именах** — `RequiredTotemCategoryID_1/2` в SQL
  против `TotemCategory_1/2` в файле. Для копирования из клиентского DBC заведён
  явный алиас (`CLONE_DBC_ALIASES`), иначе копия тотемного спелла теряла бы
  категорию тотема.

По итогам сверки в каталог полей добавлены колонки, которых там не было:
`ExcludeCasterAuraState`, `ExcludeTargetAuraState` и группа **«Реагенты и
тотемы»** (`Reagent_1-8`, `ReagentCount_1-8`, `Totem_1-2`,
`RequiredTotemCategoryID_1-2`). Реагенты использует 4 372 стоковых спелла из
49 839, категории тотемов — 1 714, так что без них копия любого рецепта или
тотема была бы тихо другой. Заодно они стали редактируемыми, а `validate()`
предупреждает про реагент без количества и наоборот.

Шесть колонок `spell_dbc` — настоящие `float` (`Speed`,
`EffectRealPointsPerLevel_*`, `EffectMultipleValue_*`, `EffectPointsPerCombo_*`,
`EffectChainAmplitude_*`, `EffectBonusMultiplier_*`). Панель читает, показывает
(`step="any"`), сохраняет и выгружает их дробными — раньше коэффициент `0.6`
превращался в `0` при первом же сохранении.

## Иконки

`docs/client_manifest.csv` хранит `icon_texture` для каждого спелла модуля — это
единственная серверная запись о том, какую иконку спелл реально показывает в игре
(настоящий `SpellIconID` лежит в клиентском `Spell.dbc` внутри MPQ; в серверной
`spell_dbc` там безобидная заглушка `1`, которую никто не читает).
Панель ищет иконку так:

1. `app/static/icons/<texture>.png` — локальный файл, если положить извлечённые
   из клиента BLP→PNG;
2. `ADMIN_ICON_BASE_URL/<texture>.jpg` — публичный CDN имён Blizzard (по умолчанию);
3. прозрачная заглушка.

Чтобы отключить обращения наружу, поставьте `ADMIN_ICON_BASE_URL=` пустым.

Каталог сначала выясняет **имя текстуры**, и только потом собирает URL по этим
же правилам. Порядок поиска имени (`spelldex.icon_texture`):

1. `spell_meta.icon_texture` — если иконку явно записали в мастерской;
2. `client_manifest.csv` — запись модуля эффектов окружения;
3. `Spell_custom.csv`, колонка 131 → `SpellIcon.dbc` / `SpellIcon_custom.csv` —
   настоящая клиентская иконка кастомного спелла;
4. `SpellIconID` из DBC/БД → `SpellIcon.dbc`.

Заглушка `SpellIconID = 1` (это `trade_engineering`, гаечный ключ) у
**добавленных** спеллов считается «иконки нет» — иначе сотня кастомных аур
показывала бы ключ. У **изменённых** стоковых спеллов при заглушке берётся
`SpellIconID` из клиентского DBC: клиент рисует именно его.

Страница спрашивает у сервера один раз (`local_icons` в `/api/dex/meta`), есть
ли каталог локальных PNG, вместо того чтобы ловить 404 на каждой из сотни строк.

Мастерская идёт тем же путём. Раньше она знала только пункт 1 —
`spell_meta.icon_texture`, который заполняется, лишь когда иконку выбрали
**в панели**, — поэтому у спеллов, заведённых модулями (окружение, фамильяры,
таланты предметов), превью было пустым, хотя каталог рисовал картинку.
Теперь `/api/spells` и `/api/spells/{id}` отдают ещё и `icon_resolved`
(`spelldex.workshop_icon`), список показывает иконку в строке, а в карточке
под полем стоит «иконка из клиента: `<texture>`».

`icon_resolved` — **только для показа**: в `spell_meta` он не пишется, иначе
одно открытие чужого спелла записывало бы его иконку как выбор оператора (а при
сохранении заодно и `SpellIconID` в `spell_dbc`, см. ниже). По той же причине
предупреждение «не задана иконка» теперь молчит, если клиент иконку всё-таки
рисует.

В мастерской имя текстуры не нужно печатать: кнопка **«Выбрать…»** (или клик по
превью) открывает сетку всех 3 228 иконок из `SpellIcon.dbc` +
`SpellIcon_custom.csv` с фильтром по имени — `GET /api/icons`. Список грузится
один раз и фильтруется на клиенте; картинки — `loading="lazy"`, так что сеть
трогают только видимые ячейки.

При сохранении панель переводит выбранную текстуру обратно в `SpellIconID`
(`spelldex.icon_id_of`) и кладёт его в строку, если там стояла заглушка `0`/`1`.
Иначе получалось расхождение: панель показывала выбранную иконку, а
«Экспорт в клиент» писал в CSV заглушку `1` — гаечный ключ на каждом спелле,
сделанном руками. Явно проставленный id не перезаписывается, а неизвестная
текстура даёт предупреждение при сохранении.

## Известная особенность DBC-CSV

Локали в выгруженных CSV **сдвинуты** относительно заголовков: русская строка
лежит на позиции `enUS + 8`, а колонка с заголовком `*_ruRU` пустая. Проверено на
`.claude/dbc/AreaTable.csv` (id 1 — «Дун Морог» на индексе 19, индекс 22 пуст).
`app/dbc.py` намеренно читает по индексу, а не по имени колонки.

## Разработка без Docker

```bash
pip install -r requirements.txt
ADMIN_DB_HOST=127.0.0.1 ADMIN_DB_PORT=3307 \
ADMIN_DB_NAME=acore_world_ptr ADMIN_DB_PASS=password \
ADMIN_REPO_ROOT=../.. ADMIN_TOKEN=dev \
ADMIN_DBC_DIR=/path/to/dbc \
uvicorn app.main:app --port 8091 --reload
```

DBC для каталога можно вытащить из контейнера:

```bash
docker cp ac-worldserver-ptr:/azerothcore/env/dist/data/dbc/Spell.dbc ./dbc/
```

API-схема — `http://127.0.0.1:8091/api/docs`.
