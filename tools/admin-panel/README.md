# admin-panel

Центральный управляющий узел сервера: одна веб-панель, из которой видно
состояние сервера, редактируется контент модулей и ведутся баги и идеи.

Страницы:

| Адрес | Что там |
| --- | --- |
| `/` | статус (БД, SOAP, счётчики) + плитки модулей |
| `/board.html` | канбан-доска: баги, идеи, задачи |
| `/envfx.html` | редактор **mod-environmental-effects** — правила зон и глобальный пул |
| `/italents.html` | редактор **mod-item-talents** — категории, пулы перков, пороги |
| `/spells.html` | мастерская спеллов — правка `spell_dbc` |
| `/dex.html` | каталог спеллов — все ~55 000, только чтение |
| `/api/docs` | схема API |

Редакторов модулей два — эффекты окружения и таланты предметов.
Остальные модули на главной значатся как «редактора пока нет», но карточки на
доске под них уже можно заводить.

Редактор талантов правит то, что раньше было зашито в C++ и в conf:
какие предметы попадают в какую категорию, из каких вариантов состоит меню
ряда (10 вариантов, роллится 3), персональные пулы конкретных эпиков и
пороги убийств по (качество, ilvl). Применяется на живом PTR командой
`.itemtalent reload` — рестарт не нужен.

Мастерская и каталог — про спеллы, но с разных сторон: мастерская правит те
несколько сотен, что мы авторим сами, каталог показывает всё, что вообще знает
сервер, и ничего не пишет.

## Оформление

Тема — «слегка WotLK»: тёмный камень, бронзовые рамки, золотые заголовки,
серифный шрифт из системного набора Windows. Цвета качества предметов
используются осмысленно, а не для красоты: приоритет карточки читается как
привычная лестница качества (серый → зелёный → фиолетовый → оранжевый).

Ни картинок, ни веб-шрифтов — всё на CSS-градиентах и одном inline-SVG
(стрелка у `<select>`), поэтому панель одинаково выглядит офлайн и в tailnet.
Единственная внешняя загрузка осталась прежней и необязательной — иконки
спеллов с CDN, см. раздел «Иконки».

Рядом лежит `app/static/style.hive.css` — альтернативная тема по образцу
hiveworkshop.com: почти чёрные плоские панели, янтарный `#f8b700`,
багрово-золотые кнопки, круглые металлические медальоны иконок, Segoe UI без
серифа. Переключиться:

```bash
cd app/static && cp style.hive.css style.css
cd ../../../.. && docker compose --profile ptr up -d --build ac-admin-panel
```

Обе темы держат один и тот же набор селекторов, так что смена файла ничего не
ломает — разметку и JS трогать не нужно.

## Границы

- **Редакторы модулей — только PTR.** `app/config.py` отказывается стартовать,
  если `ADMIN_DB_NAME` не заканчивается на `_ptr`. Обойти можно только
  `ADMIN_ALLOW_NON_PTR=1`.
- **Каталог спеллов только читает.** У `/dex.html` нет ни одного пути записи:
  том с клиентскими DBC примонтирован `:ro`, а правки идут через мастерскую.
- **Таблицы на запись** в игровой БД — `mod_environmental_effects`
  (редактор зон), `spell_dbc` (мастерская) и восемь `item_talent_*`
  (редактор талантов:
  `category`, `category_rule`, `def`, `row_cfg`, `item_def`, `item_cfg`,
  `kill_curve`, `perk_library`). Всё остальное (`item_template`,
  `game_weather`, `AreaTable.csv`, `client_manifest.csv`, клиентские DBC)
  читается.
- **Доска живёт отдельно** — в собственной схеме `acore_admin`
  (`ADMIN_BOARD_DB_NAME`), которая создаётся при первом запуске. Это не игровые
  данные, и откат PTR-снапшота не должен стирать заведённые баги. Поэтому
  `app/board.py` не ходит через `db.connect()` — у того PTR-гард, который
  `acore_admin` отверг бы по построению.
- **Один операторский токен.** Ролей пока нет; их место — `require_admin()`
  в `app/main.py`, единственная функция, которая решает «кто звонит».

## Запуск

```bash
# .env (рядом с docker-compose.yml)
ADMIN_PANEL_TOKEN=<длинная случайная строка>
ADMIN_SOAP_USER=<аккаунт acore_auth с gmlevel >= 3>
ADMIN_SOAP_PASS=<его пароль>
ADMIN_PANEL_BIND=127.0.0.1        # или tailnet-адрес

docker compose --profile ptr up -d --build ac-admin-panel
```

Открыть `http://127.0.0.1:8091/`, при первом запросе браузер спросит токен
(хранится в `localStorage`).

Статика запечена в образ, так что после правок в `app/` нужен пересбор
(`up -d --build`), а не только рестарт.

### Предпосылки на стороне сервера

1. `env/dist/etc-ptr/worldserver.conf`: `SOAP.Enabled = 1`, `SOAP.IP = "0.0.0.0"`
   (уже выставлено). Порт 7878 внутри контейнера, 7880 на хосте.
2. PTR-worldserver запущен: `docker compose --profile ptr up -d ac-worldserver-ptr`.
3. Аккаунт для SOAP: `acore_auth.account_access.gmlevel >= 3`
   (`ACSoap.cpp` требует `SEC_ADMINISTRATOR`).

Без SOAP панель остаётся рабочей — правки уходят в БД, но применяются только
после ручного `.reload config` или рестарта. Доске SOAP не нужен вовсе.

## Доска

Пять колонок: `backlog → todo → doing → review → done`. Карточка это баг
(🐞), идея (💡) или задача (🔧); у неё есть приоритет, модуль, теги,
исполнитель и комментарии.

- Перетаскивание — обычный HTML5 drag-and-drop. Дроп шлёт один
  `POST /api/board/cards/{id}/move` с колонкой и индексом, сервер отвечает
  всей доской, поэтому клиент и БД не расходятся.
- «В архив» — мягкое удаление (`archived = 1`), кнопка **Архив** в шапке
  показывает архив и позволяет вернуть карточку. Насовсем — только через API
  (`DELETE ...?hard=true`).
- С главной страницы плитка модуля ведёт на доску с уже выставленным
  фильтром (`/board.html?module=<id>`), а «＋ карточка» сразу открывает форму.

Схема (`board_card`, `board_comment`) описана в `app/board.py:SCHEMA` и
создаётся кодом — миграции в `data/sql/updates/` для неё не нужны, это не
игровая БД.

## Добавить модуль на главную

1. Запись в `app/registry.py` — `status="planned"` достаточно, чтобы под модуль
   можно было заводить карточки.
2. Когда появится редактор: страница в `app/static/`, её имя в `PAGES`
   (`app/main.py`), `status="ready"` и `url` в реестре.

Форма, которую стоит повторять для нового редактора, — `app/envfx.py`: файл на
модуль, в нём схема таблицы, `validate()`, кодирующая то, что реально читает
C++, и транзакционная замена вроде `save_zone()`.

## Что делает кнопка (эффекты окружения)

| Кнопка | Действие |
| --- | --- |
| **Применить на PTR** | валидация → запись правил зоны в одной транзакции → `.reload config` по SOAP |
| **Перезагрузить правила** | только `.reload config` |
| **Экспорт в SQL** | перезаписывает `data/sql/updates/pending_db_world/mod_env_effects_v2_seed.sql` текущим состоянием таблицы (атомарно) |

Экспорт — это то, что делает панель источником правды: состояние живёт в БД, но
попадает в git. На live правила уезжают обычным deployment-package'ом, панель
сама к live не ходит.

## Валидация

Ошибки (блокируют сохранение, можно продавить «сохранить всё равно»):

- спелла нет в `spell_dbc` — сервер молча пропустит правило при загрузке;
- дубль спелла в одном пуле;
- отрицательный `zone_id`.

Предупреждения (не блокируют):

- id вне блоков модуля (`107000-107499` баффы, `107500-107799` дебаффы) или из
  чужого блока;
- `trigger_type` у баффа / `time_flag` у дебаффа — ядро их игнорирует;
- больше трёх активных слотов **в одной корзине** (дебаффы считаются по
  триггеру, баффы — отдельно по «доступным днём» и «доступным ночью»: ротация
  выбирает внутри корзины, а не по всему пулу);
- все баффы «только днём» или все «только ночью» — с пометкой, закрывает ли
  дыру глобальный пул;
- погодный дебафф в зоне, которой нет в `game_weather` — не сработает никогда;
- триггеры «Туман», «Гроза», «Чёрный дождь», «Чёрный снег» — ядро таких
  состояний не генерирует, они сработают только если выставить погоду вручную;
- у зоны есть правило «Дождь», но ни у неё, ни в глобальном пуле нет правила
  «Гроза» / «Чёрный дождь» — в такую погоду дебаффа не будет вовсе (аналогично
  «Снег» → «Чёрный снег»).

## Глобальный пул (zone_id 0)

Первая строка в списке зон — не зона, а **умолчания для всех зон таблицы**.
Подставляются **по корзинам**: корзина — это один эффект (постоянные дебаффы,
дебаффы одной погоды, баффы, подходящие текущему времени суток). Если у зоны в
корзине нет ни одного своего правила, берутся глобальные; если есть хоть одно —
глобальные для этой корзины молчат. Смешения нет: свой дождевой пул зоны
перебивает глобальный дождевой целиком, но грозовой при этом всё равно
подставится из глобального.

Зона, у которой нет вообще ни одной строки, остаётся пустой: модуль по-прежнему
opt-in, глобальный пул закрывает дыры только в уже подключённых зонах.

С 2026-08-19 у каждой погоды **ровно один** триггер: гроза — не дождь, чёрный
дождь — не дождь, чёрный снег — не снег. Раньше грозовое правило конкурировало с
дождевым и проигрывало жребий в половине случаев; теперь редкая погода звучит
по-своему, а пробелы закрывает глобальный пул.

## Каталог спеллов

`/dex.html` отвечает на вопрос «что уже есть», в отличие от мастерской, которая
отвечает «что мы сделали сами». Он читает три источника и склеивает их в том же
порядке, что и worldserver в `LoadDBCStores`:

1. `/client-data/dbc/Spell.dbc` — 49 839 записей из тома `ac-client-data-v2`,
   ровно те байты, которые грузит PTR-сервер;
2. `acore_world_ptr.spell_dbc` — 5 262 строки, которые `LoadFromDB` кладёт
   поверх: часть переопределяет стоковые спеллы, часть добавляет новые;
3. `.claude/dbc/Spell.csv` и `Spell_custom.csv` — **только тексты**. Бинарные
   DBC извлечены из enUS-клиента, поэтому русские названия и описания берутся
   из ruRU-выгрузок, а `Spell_custom.csv` вдобавок хранит настоящий
   `SpellIconID` кастомных спеллов.

Отсюда три «источника» в фильтре и в бейдже карточки:

| Бейдж | Что значит |
| --- | --- |
| клиентский DBC | стоковый спелл, никем не тронут |
| изменён | строка есть и в DBC, и в `spell_dbc` — модуль её переписал |
| добавлен | строки нет в клиентском DBC, она существует только в БД |

Фильтры **Модуль** и **Пул ID** — те же диапазоны, что раздаёт мастерская
(`app/spells.py:BLOCKS`), поэтому «чей спелл» и «в каком диапазоне» здесь один
вопрос:

- **Модуль** перечисляет только модули **со своим диапазоном** (env-effects,
  familiars, item-talents, statbooster) — фильтровать по ID модуля без
  диапазона не по чему. В скобках — сколько спеллов каталога попадает в его
  диапазоны.
- **Пул ID** сужает до одного блока; список пулов ограничен выбранным модулем.
  Без модуля есть пункт «Все кастомные блоки» — всё, что мы завели сами
  (`block=*` в API).
- Под селектом видны сами границы (`103000-103099, занято 100 из 100`).
- Бейдж пула в карточке спелла кликабельный: показать весь пул того спелла,
  который уже нашёлся.

Счётчики считаются по самому каталогу, а не по `COUNT(*) FROM spell_dbc`: в
диапазон может попасть и стоковый спелл, переписанный модулем.

У «изменён» в карточке спелла появляется секция **Что меняет spell_dbc**:
поколоночный дифф `DBC → БД`. Это самый быстрый способ увидеть, что именно
правил модуль, не читая его SQL.

Индекс строится при первом запросе (~4 с, из них 3 — разбор `Spell.csv`) и
живёт в памяти; полная строка спелла достаётся из mmap по требованию. Запись в
`spell_dbc` из мастерской сбрасывает кэш (`spelldex.invalidate()`).

### Чтение DBC

`app/dbcfile.py` — маленькая читалка WDBC: mmap, распаковка поля по запросу,
явная раскладка колонок. Раскладка `Spell.dbc` сверена с
`.claude/dbc/Spell.csv` по именам колонок — 138 числовых колонок на выборке
спеллов сошлись до последнего значения.

Две вещи, которые стоят времени, если выводить их заново:

- поле DBC — всегда 4 байта, поэтому два `uint64` (маски стоек) занимают
  четыре поля: 234 поля в файле против 232 имён колонок;
- локализованная строка — 17 полей (16 смещений + маска), и **ruRU лежит в
  слоте 8**. Это и есть тот самый сдвиг «ruRU = enUS + 8», который вылезает во
  всех CSV-выгрузках.

### Справочники для мастерской

Поля `DurationIndex`, `CastingTimeIndex`, `RangeIndex` и `EffectRadiusIndex` —
не числа, а индексы в отдельных DBC. Одноимённые таблицы `spellduration_dbc`,
`spellcasttimes_dbc`, `spellrange_dbc`, `spellradius_dbc` в игровой БД **пусты**
(сервер читает файлы), поэтому `spells.refs()` берёт варианты из DBC и кладёт
строки из БД поверх — тем же порядком, что и ядро. Получается 130 длительностей,
70 времён каста, 64 дальности, 58 радиусов вместо одного значения.

Значения, которые стоит помнить (сверено по `SpellDuration.dbc`):

| Индекс | Длительность |
| --- | --- |
| 21 | постоянная (`-1`) |
| 5 | 5 минут |
| 9 | **30 секунд** |

Пару «9 = 5 минут» из старых заметок можно смело забыть — это 30 секунд.

### Что нужно примонтировать

```yaml
volumes:
  - ac-client-data-v2:/client-data:ro   # Spell.dbc и остальные справочники
  - ./.claude/dbc:/repo/.claude/dbc     # Spell.csv, Spell_custom.csv, SpellIcon_custom.csv
environment:
  ADMIN_DBC_DIR: /client-data/dbc
```

Без тома каталог честно скажет «недоступен», остальная панель работает как
раньше. Без `.claude/dbc` каталог останется английским.

## Модуль и пул ID

Каждый модуль владеет диапазоном ID в `spell_dbc` (`app/spells.py:BLOCKS`), а
новый спелл получает **первый свободный ID своего пула**. Поэтому у черновика
модуль и ID — одно решение, и панель показывает их вместе, в группе
«Панель: модуль, иконка, заметка» (она открыта сразу):

- **Модуль** — список из `app/registry.py`, то есть тот же, что на главной.
  Смена модуля у *нового* спелла переносит его в диапазон этого модуля;
  у модуля без своего диапазона черновик уходит в «Мастерскую» (109000-109999).
- **Пул ID** — сам диапазон, если у модуля их несколько (у фамильяров три, у
  талантов предметов тоже: `108000-108049` скрытые триггеры проков ряда 5,
  `108050-108099` их видимые эффекты, `108900-108999` ауры рядов 1-4). Под селектом — `ID 109003 · занято 3 из 1000 (109000-109999)`, где ID
  берётся живым запросом `GET /api/spells/next-id?block=<id>`, а не из кэша
  страницы.
- У **сохранённого** спелла пул только показывается: сменить его — значит
  сменить ID, то есть завести другой спелл (для этого есть «Копировать»).
- В окне **⧉ Копия** пул выбирается до копирования, там же видно, какой ID
  получит копия.

Канон списка — `app/spells.py:BLOCKS`, и он должен покрывать всё, что мы
авторим: диапазон без блока не виден ни в фильтре мастерской, ни в фильтре
каталога, то есть спеллов будто нет. Сверка `GROUP BY FLOOR(ID/100)` по
`spell_dbc` от 2026-08-19 нашла три таких дыры — оба пула проков ряда 5
mod-item-talents (86 спеллов), ночной дебафф окружения `108500` и
`105000` от mod-gear-ascension; все три теперь блоки. Намеренно не
размечены чужие ID: `91003` (апстрим AzerothCore) и `200100`
(апстримный mod-transmog).

## Копия существующего спелла

Самый быстрый способ завести новый спелл — взять готовый. Копируются **все**
поля, кроме названия (`Name_Lang_ruRU` / `Name_Lang_enUS`): два спелла с
одинаковым именем неразличимы ни в тултипе, ни в боевом логе, ни в списке
мастерской.

Три входа:

| Откуда | Что делает |
| --- | --- |
| **⧉ Копия** в шапке мастерской | поиск по всему каталогу → выбор источника |
| **Копировать** в карточке открытого спелла | копия текущего |
| **Копировать в мастерскую** в каталоге | `/spells.html?clone=<id>` |

Источником может быть что угодно: свой спелл, стоковый спелл Blizzard или
стоковый, переписанный модулем. Поля берутся из того же слияния, что показывает
каталог (`DBC → spell_dbc`), русские тексты — из `Spell.csv`, иконка — из
`spell_meta` / `Spell_custom.csv` / `SpellIcon.dbc`.

`GET /api/spells/clone/{id}?block=workshop` **ничего не пишет**: он отдаёт
черновик с уже выданным свободным ID, а сохраняет обычный `POST /api/spells` —
то есть копия проходит ту же валидацию, что и спелл, набранный руками.

Черновик может вернуть предупреждения:

- у стокового источника — напоминание, что скрипты ядра, привязанные к его ID,
  на копию не перейдут (копируются только поля DBC);
- поля, которых нет в каталоге полей, — в копии они останутся нулевыми;
- дробные значения в целочисленных колонках, если такие попались.

### Что именно копируется (сверено по колонкам)

Каталог полей закрывает **все функциональные колонки** `spell_dbc`: 234 колонки
таблицы = 171 в белом списке панели (`ID` + 170 редактируемых) + 63, которые
никому не нужны. Сверено против `information_schema` и клиентского `Spell.dbc`:

| Колонки | Статус |
| --- | --- |
| 170 боевых (эффекты, атрибуты, тайминги, требования, реагенты) + `ID` | копируются |
| 57 колонок других локалей (`*_Lang_deDE` и т.п.) | не трогаем: панель ведёт ru/en |
| 4 маски локалей (`Name_Lang_Mask` и т.п.) | всегда `0`, в том числе у всех строк модулей |
| `unk_320_2`, `unk_320_3` | старшие 32 бита `ShapeshiftMask`/`ShapeshiftExclude`; `0` во всех 5 262 строках БД, и ни один стоковый спелл не выходит за 32 бита |

Две вещи, которые стоило проверить и которые оказались верны:

- **порядок колонок таблицы совпадает с порядком полей в DBC** (166 к 166 после
  разворачивания двух `uint64` в пары `int`). Это важно, потому что панель
  пишет по именам, а `DBCStorage::LoadFromDB` читает по позициям. Косвенное
  подтверждение: строки модулей, переписывающие стоковые спеллы, отличаются от
  файла в 1-5 колонках из 141, а не во всех;
- **единственное расхождение в именах** — `RequiredTotemCategoryID_1/2` в SQL
  против `TotemCategory_1/2` в файле. Для копирования из клиентского DBC заведён
  явный алиас (`CLONE_DBC_ALIASES`), иначе копия тотемного спелла теряла бы
  категорию тотема.

По итогам сверки в каталог полей добавлены колонки, которых там не было:
`ExcludeCasterAuraState`, `ExcludeTargetAuraState` и группа **«Реагенты и
тотемы»** (`Reagent_1-8`, `ReagentCount_1-8`, `Totem_1-2`,
`RequiredTotemCategoryID_1-2`). Реагенты использует 4 372 стоковых спелла из
49 839, категории тотемов — 1 714, так что без них копия любого рецепта или
тотема была бы тихо другой. Заодно они стали редактируемыми, а `validate()`
предупреждает про реагент без количества и наоборот.

Шесть колонок `spell_dbc` — настоящие `float` (`Speed`,
`EffectRealPointsPerLevel_*`, `EffectMultipleValue_*`, `EffectPointsPerCombo_*`,
`EffectChainAmplitude_*`, `EffectBonusMultiplier_*`). Панель читает, показывает
(`step="any"`), сохраняет и выгружает их дробными — раньше коэффициент `0.6`
превращался в `0` при первом же сохранении.

## Иконки

`docs/client_manifest.csv` хранит `icon_texture` для каждого спелла модуля — это
единственная серверная запись о том, какую иконку спелл реально показывает в игре
(настоящий `SpellIconID` лежит в клиентском `Spell.dbc` внутри MPQ; в серверной
`spell_dbc` там безобидная заглушка `1`, которую никто не читает).
Панель ищет иконку так:

1. `app/static/icons/<texture>.png` — локальный файл, если положить извлечённые
   из клиента BLP→PNG;
2. `ADMIN_ICON_BASE_URL/<texture>.jpg` — публичный CDN имён Blizzard (по умолчанию);
3. прозрачная заглушка.

Чтобы отключить обращения наружу, поставьте `ADMIN_ICON_BASE_URL=` пустым.

Каталог сначала выясняет **имя текстуры**, и только потом собирает URL по этим
же правилам. Порядок поиска имени (`spelldex.icon_texture`):

1. `spell_meta.icon_texture` — если иконку явно записали в мастерской;
2. `client_manifest.csv` — запись модуля эффектов окружения;
3. `Spell_custom.csv`, колонка 131 → `SpellIcon.dbc` / `SpellIcon_custom.csv` —
   настоящая клиентская иконка кастомного спелла;
4. `SpellIconID` из DBC/БД → `SpellIcon.dbc`.

Заглушка `SpellIconID = 1` (это `trade_engineering`, гаечный ключ) у
**добавленных** спеллов считается «иконки нет» — иначе сотня кастомных аур
показывала бы ключ. У **изменённых** стоковых спеллов при заглушке берётся
`SpellIconID` из клиентского DBC: клиент рисует именно его.

Страница спрашивает у сервера один раз (`local_icons` в `/api/dex/meta`), есть
ли каталог локальных PNG, вместо того чтобы ловить 404 на каждой из сотни строк.

Мастерская идёт тем же путём. Раньше она знала только пункт 1 —
`spell_meta.icon_texture`, который заполняется, лишь когда иконку выбрали
**в панели**, — поэтому у спеллов, заведённых модулями (окружение, фамильяры,
таланты предметов), превью было пустым, хотя каталог рисовал картинку.
Теперь `/api/spells` и `/api/spells/{id}` отдают ещё и `icon_resolved`
(`spelldex.workshop_icon`), список показывает иконку в строке, а в карточке
под полем стоит «иконка из клиента: `<texture>`».

`icon_resolved` — **только для показа**: в `spell_meta` он не пишется, иначе
одно открытие чужого спелла записывало бы его иконку как выбор оператора (а при
сохранении заодно и `SpellIconID` в `spell_dbc`, см. ниже). По той же причине
предупреждение «не задана иконка» теперь молчит, если клиент иконку всё-таки
рисует.

В мастерской имя текстуры не нужно печатать: кнопка **«Выбрать…»** (или клик по
превью) открывает сетку всех 3 228 иконок из `SpellIcon.dbc` +
`SpellIcon_custom.csv` с фильтром по имени — `GET /api/icons`. Список грузится
один раз и фильтруется на клиенте; картинки — `loading="lazy"`, так что сеть
трогают только видимые ячейки.

При сохранении панель переводит выбранную текстуру обратно в `SpellIconID`
(`spelldex.icon_id_of`) и кладёт его в строку, если там стояла заглушка `0`/`1`.
Иначе получалось расхождение: панель показывала выбранную иконку, а
«Экспорт в клиент» писал в CSV заглушку `1` — гаечный ключ на каждом спелле,
сделанном руками. Явно проставленный id не перезаписывается, а неизвестная
текстура даёт предупреждение при сохранении.

## Известная особенность DBC-CSV

Локали в выгруженных CSV **сдвинуты** относительно заголовков: русская строка
лежит на позиции `enUS + 8`, а колонка с заголовком `*_ruRU` пустая. Проверено на
`.claude/dbc/AreaTable.csv` (id 1 — «Дун Морог» на индексе 19, индекс 22 пуст).
`app/dbc.py` намеренно читает по индексу, а не по имени колонки.

## Разработка без Docker

```bash
pip install -r requirements.txt
ADMIN_DB_HOST=127.0.0.1 ADMIN_DB_PORT=3307 \
ADMIN_DB_NAME=acore_world_ptr ADMIN_DB_PASS=password \
ADMIN_REPO_ROOT=../.. ADMIN_TOKEN=dev \
ADMIN_DBC_DIR=/path/to/dbc \
uvicorn app.main:app --port 8091 --reload
```

DBC для каталога можно вытащить из контейнера:

```bash
docker cp ac-worldserver-ptr:/azerothcore/env/dist/data/dbc/Spell.dbc ./dbc/
```

API-схема — `http://127.0.0.1:8091/api/docs`.
